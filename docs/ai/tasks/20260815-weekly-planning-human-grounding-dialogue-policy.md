## 1. 目的

StudyPlanner の週間計画対話を、固定質問を順番に読み上げるフォームではなく、ユーザーとの共同活動として成立する対話にする。

同じmachine decisionでも、それまでの発話系列、直前のユーザー発話、共有済みの語彙、その時点の共通基盤に応じて自然な表現は変わる。特定の完成済み日本語文を正解として固定しない。

## 2. 共通基盤の最重要原則

Fact Graphやapplication stateに情報が存在することと、ユーザーとの共通基盤にその情報が入っていることは別である。

特に次を区別する。

```text
application internally knows X
≠ user and application have mutually established X
```

内部heuristic、一般原則、推奨方針、推定結果を、ユーザーも当然知っている前提で話してはならない。

禁止例:

- まだ短時間学習を提案していないのに「短めに分けるだけだと難しいので」と話す。
- まだ復習分散を共有していないのに「いつもの分散復習で」と話す。
- applicationだけが知る推定を、以前から合意済みの事実のように省略する。

必要な方針は会話上へ提示し、理由が共同作業上有用なら短く説明し、ユーザーのaccept / reject / modifyを受けて初めて共有済み方針として扱う。

```text
internal candidate
→ proposal becomes observable
→ user accepts / rejects / modifies
→ accepted scope becomes shared ground
```

## 3. 了承のscopeを越えない

「今回はそうして」と「今後もそれを基本にして」は同じ意味ではない。

applicationは、ユーザーがどのscopeについて了承したかをtyped stateで保持する。

- current turn / current planだけ
- current week
- current task / component
- durable user preference

週内の提案への了承を、根拠なく恒常的なユーザー特性へ昇格させない。長期利用を提案し、そのscopeが明示的に了承された場合のみdurable preferenceへ昇格できる。

ユーザー自身が最初から「いつも」「今後は」「基本的に」等の恒常的な意味を述べた場合は、AI semantic layerがそのscopeを構造化し、applicationがdurable保存可否を決める。

## 4. 人間を完全なフォーム入力者と仮定しない

ユーザーは協力的でも省力的である。

- 質問されたことだけ短く答える。
- 省略語・指示語を使う。
- 後から情報を追加する。
- 一度言ったことを訂正する。
- 必要情報を一発話に体系的にまとめない。

real-API conversationでも、ユーザー役に最終的なfactsを一度に全部言わせない。各assistant turnを読んで、その時点で自然な最小限の返答を次turnとして与える。

## 5. Observable grounding

共通基盤は内部保存だけでは成立したとみなさない。共同作業上必要な場合は、理解の証拠を会話上から観察可能にする。

候補:

- acknowledgement
- confirmation
- paraphrase
- ユーザー自身の語彙の再利用
- 訂正内容の反映
- deterministicに確定した帰結の提示
- accepted proposalの再利用

ただし毎回「分かりました」を付ける固定規則にはしない。理解が十分で進行可能なら過剰確認を避け、重要な不一致や未共有前提だけを修復する。

## 6. AI / application責務

### AI semantic layer

AIはraw user textと必要な会話文脈からcurrent-turn semantic deltaを構造化する。

- task / component / workload
- quantity role
- date / weekday / time intent
- correction
- contextual reference
- proposalへのaccept / reject / modification
- current-only / durable等のscope意味

AI semantic boundary以後のdeterministic codeはraw Japanese textをregex、keyword、dictionary等で再解釈して意味を作り直さない。

### Deterministic application

applicationは次を所有する。

- schema / evidence / reference validation
- formal binding
- Fact Graph lifecycle / revision / idempotency
- confirmation necessity / question priority
- proposal candidate / proposal lifecycle
- acceptance scope
- readiness
- scheduler / placement
- preview / approval / save
- persistence / recovery
- observed pace / learning evidence等の計算

「何を聞くか」「何を提案するか」「了承後に何を採用するか」はapplication decisionである。

### AI dialogue renderer

rendererはtyped application decisionとgrounded contextを自然な対話へ実現する。

rendererは、まだ共有されていない内部heuristicを既知前提として表現しない。applicationが選んだ提案理由・候補・現在の共有状態を使い、必要な前提を会話上へ導入してから質問する。

rendererは新しいfact、confirmation requirement、proposal acceptance、schedule、save decisionを発明しない。

## 7. 固定文・prompt方針

正常系でquestion codeやproposal codeごとの完成済み日本語文をsource of truthにしない。

promptは次の一般原則に限定する。

- ongoing collaborative dialogueとして話す。
- current shared groundを尊重する。
- application-only knowledgeをshared premiseとして扱わない。
- 必要なら提案や理由を先にobservableにする。
- partial / economical user inputを通常とする。
- unresolved pointを一度に一つ扱う。
- harmless differenceを過剰修復しない。
- applicationが決めていないfact / decision / scheduleを発明しない。

特定発話の回帰を塞ぐために完成済み返答例をproduction promptへ追加しない。

## 8. Proposal dialogue contract

proposalはcommandではない。

```text
candidate generated by application
→ renderer presents it naturally
→ semantic AI interprets response
→ deterministic application accepts / rejects / modifies
→ accepted policy affects scheduling
```

proposalを提示しただけでschedulerへ適用しない。

「おすすめ」「一般的には有効」等の情報と、「このユーザーが今回採用した方針」を別stateとして扱う。

## 9. Memory grounding contract

週・conversationで成立した方針と、owner-scoped durable preferenceを区別する。

- current-week acceptance: その計画のshared ground
- durable acceptance: 今後も使うことまで共有されたuser preference
- observed profile: applicationが実行結果から観測した特性であり、本人の明示preferenceとは別

長期記憶を次回会話で利用する場合も、必要なら「これまで20分前後を基本にしていました」のように短く再groundingし、黙って絶対ルールとして適用しない。

## 10. Real-API acceptance

各turnで最低限確認する。

1. user contributionをsemantic AIが正しく解釈したか。
2. applicationが共有済みでない前提を勝手に確定していないか。
3. rendererが内部heuristicをshared premiseとして話していないか。
4. proposalが了承前にschedulerへ適用されていないか。
5. accepted scopeを越えて長期記憶へ昇格していないか。
6. acknowledgement / paraphraseが必要なturnで共有理解がobservableか。
7. 次に何を答えればよいか人間から見て明確か。

明確な違反があればそのturnで停止し、原因層を直し、対象回帰→full CI→同地点real-API再実行を行う。
