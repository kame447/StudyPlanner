## 1. 全体像

週間計画は一つの巨大なstateへ直接書き込まない。次の4段階に分ける。

```text
ユーザーの発話
  ↓
1. 意味文書
   AIが発話を汎用的な意味構造へ写す
  ↓ 厳密検証
2. 正式な事実グラフ
   coreが正式ID・revision・参照関係を発行する
  ↓ 日付・外部予定・固定予定を決定論的に解決
3. 解決済みの計画材料
   可動作業、固定予定、実行可能日、空き時間、使用中の予定元
  ↓ readiness / authorization
4. scheduler入力
   schedulerが配置だけを担当する
```

AIが決めるのは「発話が何を意味しているか」までである。予定を作れるか、何を質問するか、どこへ配置するか、保存するかは後段が決める。

個人最適化profileはこの4段階とは別のアカウント単位stateである。単発の発話から直接上書きせず、明示設定または計画と実績の集計から更新する。

## 2. 意味文書

意味文書は一回のユーザー発話から読み取った内容である。まだdatabase stateでもscheduler requestでもない。

```text
意味文書
├─ 発話の目的
│  └─ 新規作成 / 更新 / 相談 / 不明
├─ 計画全体の期間
├─ タスク
├─ タスク間の関係
├─ 計画全体の空き時間・利用不可時間・希望時間
├─ 外部予定を使う・使わないという要求
├─ 不確かな点
├─ 修正要求
└─ 提案への判断
```

### タスク

```text
タスク
├─ 種類
│  └─ 学習 / 学習以外 / 不明
├─ 名前
├─ 学習情報
├─ 作業量
├─ 所要時間の見積り
├─ そのタスク固有の日時条件
├─ そのタスクの実行日・除外日
└─ 繰り返し
```

院試、資格試験、大学受験、宿題、研究、家事を別々の最上位schemaにしない。すべてタスクとして扱い、必要な場合だけ学習情報を持たせる。

### 学習情報

```text
学習情報
├─ 目的
│  └─ 試験 / 授業 / 宿題 / 自習 / 演習 / 復習 / 習慣 / 研究 / その他 / 不明
├─ 文脈名
│  └─ 大学院入試、TOEIC、基本情報など
└─ 構成要素
   └─ 科目 / 分野 / 教材 / 単元 / 章 / 節 / 技能 / 独自分類
```

構成要素は親子関係を持てる。

```text
大学院入試
└─ OS・ネットワーク
   └─ 2024年度過去問
```

### 作業量

```text
作業量
├─ 量
├─ 単位
│  └─ 分 / 時間 / ページ / 問 / 語 / 回 / 章 / 節 / 年分 / 模試 / 独自単位
├─ 量の意味
│  └─ 明示された量 / 今回の目標 / 残量 / 完了量 / 不明
├─ 実際の範囲
├─ 1回あたりか
└─ 対象期間
```

「2年分あります」のように、その2年分が総量・残量・今回目標のどれか確定できない場合は、無理に決めず「明示された量」として保持する。

### 所要時間

作業量と所要時間を分離する。

```text
20問
→ 作業量

1問10分
→ 1単位あたりの所要時間

全部で3時間
→ 合計所要時間
```

### 日時条件

タスク固有の条件だけをタスク内へ置く。

```text
研究は15時まで
夕食は18時から19時
英単語は寝る前
```

日時条件は次を分離する。

```text
日時条件
├─ 日付
├─ 名前付き時間帯
├─ 開始時刻
├─ 終了時刻
├─ 条件の種類
└─ 強さ
   └─ 必須 / 希望 / 不明
```

「明日」と「午前中」を同じfieldへ入れない。日付はcanonical token、時間帯は別fieldとして保持する。

## 3. 特定日の計画と例外日

特定日の要求は、意味の異なる三種類へ分ける。

### 3.1 計画期間自体が一日

```text
7月24日の予定を立てたい
→ 計画開始日 = 2026-07-24
→ 計画終了日 = 2026-07-24
```

一週間を必須としない。開始日と終了日が同じabsolute planning windowを通常の計画期間として扱う。

### 3.2 特定タスクをその日だけ行う・行わない

```text
英単語は24日だけやる
→ task allowed date = 2026-07-24

25日は英単語をやらない
→ task excluded date = 2026-07-25
```

タスクの日付ルールは次を持つ。

```text
タスク日付ルール
├─ 対象タスク
├─ 種類
│  ├─ その日だけ実行可能
│  └─ その日は実行不可
├─ 日付表現
├─ 必須条件
└─ 根拠となる発話
```

複数の実行可能日は和集合とし、除外日はそこから差し引く。実行可能と除外が同じ日に指定された場合は勝手に優先せず、どちらを採用するか一件だけ確認する。

繰り返し固定予定にも同じ例外日を適用する。

```text
毎日18時に夕食
ただし25日は入れない
→ 25日以外の固定予約だけを生成
```

### 3.3 計画全体でその日を休みにする

```text
24日は何も予定を入れない
→ 2026-07-24 00:00
   から
   2026-07-25 00:00
   までのhard unavailable window
```

これは特定タスクの除外ではなく、計画全体に適用する終日利用不可である。

## 4. 計画全体のavailability

特定タスクではなく、計画全体へ適用する時間条件である。

```text
平日は18時まで勉強できない
土日の午前中がやりやすい
明日は20時以降空いている
24日は何も予定を入れない
```

```text
availability宣言
├─ 利用可能 / 利用不可 / 希望 / 回避
├─ 日付
├─ 名前付き時間帯
├─ 開始・終了時刻
├─ 繰り返し
├─ 曜日
└─ 必須 / 希望 / 不明
```

hardな利用不可宣言が日付だけを持ち、時刻を持たない場合は終日利用不可として解決する。他の種類で時刻が欠ける場合は推測しない。

## 5. 外部予定

AIは時間割やカレンダーの予定本文を生成しない。意味文書に入るのは、ユーザーがその予定元を使うか使わないかという要求だけである。

```text
時間割も考慮して
→ 時間割のactive sourceを使う要求

カレンダーは使わないで
→ カレンダーの利用停止要求
```

実際の予定取得は別の取得層が行う。

```text
外部予定取得
├─ 成功
│  ├─ source ID
│  ├─ owner
│  ├─ 予定一覧
│  └─ 取得回数
└─ 失敗
   ├─ 原因
   └─ 取得回数
```

成功時の予定一覧が空配列なら「予定なし」という正常結果である。

```text
success(events=[])
→ 登録予定なし
→ 通常どおり計画作成を継続
```

`partial`状態は設けない。pagination等の途中で失敗した場合、取得層は途中結果を破棄して自動再試行し、全件成功か失敗だけを返す。

```text
1ページ目成功
2ページ目失敗
→ 1ページ目だけを返さない
→ 自動再試行
→ 全ページ成功ならsuccess
→ 再試行上限後も失敗ならfailure
```

通信・timeout・rate limit・一時的server errorだけを自動再試行する。認証切れ、権限不足、未設定、壊れた応答は即座に具体的な対応へ進む。

外部予定取得が失敗しても、会話、入力済みタスク、作業量、所要時間、その他の質問は保持・継続する。ユーザーが利用を求めた外部予定を確認できていない間だけ、その予定を反映した最終previewを出さない。

## 6. 正式な事実グラフ

意味文書を検証後、coreが正式IDへ変換する。

```text
正式な事実グラフ
├─ 計画期間
├─ タスク
├─ 学習文脈
├─ 構成要素
├─ 作業量
├─ 所要時間
├─ タスク固有の日時条件
├─ タスクの日付ルール
├─ 繰り返し
├─ タスク間関係
├─ availability宣言
├─ 外部予定利用要求
├─ 不確かな点
├─ 修正要求
└─ 判断要求
```

各事実は独立しているため、「OSの量だけ修正する」「英単語の25日除外だけ削除する」場合に、他タスクの情報を巻き込まずに変更できる。

現時点では追加factの生成まで実装済みであり、既存factへの修正・削除の実適用は次gateである。

## 7. 解決済みの計画材料

正式な事実から決定論的に次を作る。

```text
解決済み材料
├─ 可動作業
│  └─ 空いている時間へ配置する作業
├─ 固定予定
│  └─ 夕食、授業、固定時刻の研究など
├─ タスクごとの実行可能日・除外日
├─ availability window
│  └─ 利用不可、利用可能、希望、回避、外部予定
├─ 使用中の外部予定元
└─ タスク間関係
```

固定予定になったタスクは、同時に可動作業として別の時間へ配置しない。特定日の除外で固定予約が消えても、そのタスクを可動作業へ戻さない。

## 8. scheduler入力

schedulerへ渡すのは、解釈済みの完全な入力だけである。

```text
scheduler入力
├─ 所有者
├─ fact graphのrevision
├─ 計画期間とtimezone
├─ 可動作業
├─ 固定予定
├─ タスクごとの実行可能日・除外日
├─ availability window
├─ 外部予定元の選択
├─ タスク間関係
└─ 根拠となるfact ID
```

未解決の必須条件がある場合、schedulerへ不完全な配列を渡さない。ただし計画セッションを終了するわけではない。readinessが次の確認事項を一件選び、入力済み内容を保持したまま対話を続ける。

## 9. 個人最適化profile

個人最適化は意味文書や一回の計画factへ混ぜない。アカウント単位のversion付きprofileとして保持する。

```text
個人最適化profile
├─ schema version
├─ 週の開始曜日
├─ 科目ごとの所要時間補正
├─ 好みのセッション長
└─ 配置学習model
   ├─ feature version
   ├─ weight version
   └─ 文脈別parameter
```

### 9.1 保存する係数

配置学習modelは次のような個人差を表す係数を保存できる。

```text
完了しやすさ
開始遅延の起こりやすさ
中断されやすさ
再配置されやすさ
時間帯との相性
曜日との相性
セッション長との相性
科目切替の負担
就寝時刻への近さによる負担
一日の詰め込み量への負担
科目との相性
```

parameterは単なる数値ではなく、次を持つ。

```text
parameter
├─ 何の特徴か
├─ どの文脈か
│  └─ 夕方 / 月曜 / 数学 / 45分session等
├─ 係数
├─ 対象scope
│  └─ 全体 / 科目 / タスク
├─ 根拠
│  └─ 明示設定 / 計画と実績 / 集計結果
├─ 信頼度
├─ 更新日時
└─ model version
```

係数は範囲を制限し、不正値や未知の特徴を読込時に除外する。旧profileは空の配置学習modelを持つ新versionへ移行する。

### 9.2 保存しないもの

全ユーザー共通の基本重みはユーザーprofileへ複製しない。共通重みはmodel versionで管理し、profileにはユーザー固有の補正値とその根拠だけを保持する。

AIが会話から係数を直接決めて保存することもしない。会話で明示された好みは確認済み設定として扱い、行動から学習する値は計画と実績の対応が確認できた集計から更新する。

### 9.3 現在の接続状態

version付き保存枠とvalidationは実装済みである。ただし、この係数をproduction schedulerの配置scoreへ適用する処理と、計画実績から係数を更新するlearning pipelineは未接続である。

## 10. previewと保存

previewには次のすべてが必要である。

```text
scheduler入力が完成している
ユーザーが明示的に予定作成を許可している
許可したconversationが一致している
許可したrevisionから情報が変わっていない
```

previewは未保存であり、画面上での明示承認後にだけ保存する。
