## Local implementation checkpoint (13:14 UTC)

- The supplied follow-up image was inspected directly. Oversized vertically stacked cards and the manual date/use form were replaced by a compact hero, three-value summary, and a calendar that fills the available viewport height. All month-navigation controls remain at least 44px; date cells are non-interactive. Text enlargement and error content may scroll rather than become unreachable.
- Both flames use the same normalized positive-study-date predicate as the domain model. A current-day real study record enables the lightweight sway; rest-only, zero-duration/foreign/future data, corrections and date changes do not. Hidden tabs remove the active animation class; reduced motion disables animation in CSS. The old unconditional Home entrance animation is overridden.
- A single provider inside the existing local-date clock owns the controller for Home and detail. Unlike two hooks or a detail-only reader, this avoids an extra read on open/reopen and enables automatic protection on application return. The old summary callback and duplicated state were removed. The provider waits for the current owner's planner snapshot to be ready, preventing a premature empty-input read before the startup receipt exists. Planner load failure uses its existing retry action.
- Existing confirmed values remain visible during background refresh; unknown values remain `—`. Owner, input-reference, context-day and model-day checks guard the Home summary. `aria-busy` conveys refresh without additional visible copy. A model projected from confirmed cached history is a reference value while refreshing or after a read/save error; only a non-refreshing, error-free result represents the newest successful confirmation. New protection is never displayed before persistence acknowledges it.
- Automatic consumption policy: local yesterday and earlier only, oldest eligible gap first after a complete confirmation on startup/return/date change/history correction. Existing manually protected days retain priority. Failed reads/writes do not create new protection; acknowledged values remain available. Seven actual study days earn one ticket; rest days protect continuity but do not earn study credit. No expiry or holding cap. Schema and Firestore Rules are unchanged.
- Domain owner reports that matching planner startup receipts require zero extra full Actual/Plan queries and one rest-document read; missing/freshness-invalid proof requires complete revalidation. Exact operation-count tests belong to the domain evidence, not a performance inference from the UI.
