# Hy Memory 2.0 integration — candidate discovery spike

Status: experimental adapter, not connected to runtime
Date: 2026-10-17
Owner: #294

This spike follows the canonical user-context architecture, lifecycle policy, and roadmap. It does not mark UC-P0 or UC-P1 complete, change the existing V5 planning behavior, or provision any external service.

## Scope and decision

Evaluate `hy-memory==2.0.2` as an optional index and memory-processing engine. Firestore and the owning product domains remain authoritative for user context, schedules, learning materials, and progress.

Replacing the canonical memory store was rejected because it would create a second owner for updates, provenance, and forgetting. Running the Python SDK in a browser or existing TypeScript Cloudflare Worker was rejected because of SDK dependencies and the trust boundary. A private server-to-server Python integration remains an evaluation candidate, not a production dependency.

For Laplance user memories, begin with Hy Memory's `chat` scene. Compare `lite` embedding retrieval with the existing lexical/entity baseline before separately evaluating `pro` LLM extraction/reconciliation. `coding` scene and MemHub target developer agents and are not app user-context requirements.

## Read boundary implemented

`src/features/userPlanningContext/hyMemoryCandidateBridge.ts` accepts only ordered canonical source record IDs, owner ID, and the exact indexed source revision. It resolves them against the current authoritative snapshot, excludes other owners and all non-active records, de-duplicates results, and applies an explicit result bound. A successful no-match is distinguished from unavailable or stale index results. Content, score, or a profile generated by Hy Memory is never promoted directly to product truth.

These canonical IDs are not the Hy Memory SDK's `memory_id`. The eventual Python service must prove the mapping from its results to the original source ID/revision. The SDK supports add-time metadata and returns result `meta`, but propagation through summarization, reconciliation, and deduplication must be tested independently. An ambiguous mapping must not be guessed.

The read boundary is not connected to the planner yet. No network calls, provider secrets, database migrations, live user writes, or feature flag activation are included in this PR.

## Next vertical slices

After the existing revision/provenance/forget foundation required by #294, use synthetic Japanese cases to exercise the SDK's `add/search/delete` APIs and the source metadata mapping in `lite` and `pro` modes. Verify crash/restart durability, concurrent revisions, index errors and physical deletion; choose a persistent vector backend and authenticated server-to-server transport after this experiment.

An authoritative committed event should enqueue a bounded index update. Staged/cancelled turns and assistant suggestions must not create confirmed memories. The reader must load the latest authoritative owner/revision, fetch ranked candidates through the private service, then re-check lifecycle and scope before injecting any memory into the conversational context. Index outages or stale results must fall back to the tested baseline without blocking planning/save. Forgotten records must be excluded immediately by the authoritative read gate while separate verified cleanup removes indexed content and derived summaries.

Production use additionally requires explicit treatment of data disclosure to an external LLM/embedding provider, server authentication, retry/idempotence, index deletion, latency, and ongoing cost. No real user memory is sent during this spike.

## Acceptance evidence

Tests cover active/wrong-owner/revoked/superseded filtering, stale revision/unavailable/no-match distinctions, duplicate identifiers, and bounded projection. Those tests do not prove actual SDK behavior.

Compare the same human-reviewed Japanese evaluation cases against the existing baseline using retrieval miss, false/stale recall, per-turn context size, p50/p95 latency, provider calls, and cost. Keep Jev rerank and Hy Memory retrieval changes in separate evaluation units.
