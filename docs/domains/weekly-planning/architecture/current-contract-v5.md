## Runtime baseline

Stable V5 is the sole production weekly-planning runtime.

```text
raw user utterance + relevant conversation + typed machine state
→ AI semantic interpretation
→ schema / evidence / reference / payload-value validation
→ deterministic formal binding / canonical Fact Graph
→ deterministic proposal / repair / readiness / question / scheduler decision
→ AI dialogue renderer
→ preview
→ deterministic approval / save / persistence
```

There is no production semantic rollback path to a legacy parser/interpreter/runtime selector. The conversation architecture switch ([below](#runtime-conversation-architecture-mode-issue-488-comparison-switch)) does not reintroduce one: it selects between two Stable V5 conversation-interaction variants with the same semantic authority (one AI owner of raw Japanese, same Fact Graph/planner/approval), not a legacy parser or runtime.

Issue #246 defines a planned pre-scheduling consultation/advice extension in [learning-consultation-and-advice.md](../spec/learning-consultation-and-advice.md). Until that runtime implementation is merged and verified, the flow above remains the production baseline. The requirement document must not be read as evidence that consultation routing or AdviceProposal state already exists in production.

## Ownership

AI owns natural-language meaning and natural realization of typed dialogue decisions.

Deterministic application owns schema/evidence/reference validation, canonical IDs, binding, revision/idempotency, Fact Graph lifecycle, question/confirmation necessity, repair agenda, proposal lifecycle, readiness, scheduler/placement safety, preview freshness, approval/save, persistence/recovery and deterministic calculation.

After the semantic boundary, raw Japanese must not be reinterpreted by regex, keyword, dictionary or legacy parser as semantic truth.

For the planned Issue #246 extension, whether a user turn semantically asks for learning consultation/advice is also a natural-language meaning decision. Deterministic routing may consume a validated typed consultation contribution, but must not establish that meaning by a second raw-text keyword/regex router.

## Semantic delta

AI output is a current-turn semantic delta, not an accepted-state snapshot. Past facts are not recopied without current evidence. Formal IDs, revision, lifecycle mutation and scheduler decisions are not AI-owned.

When a validated turn explicitly corrects a planning window, canonical staging must not implicitly supersede its still-active target before the correction transaction validates it. Apply the explicit correction first, then reconcile the single-active-window invariant within the semantic commit before scheduling or persistence. Stale revisions, unknown or already-terminal targets, and invalid replacements still reject atomically with the original graph unchanged. Both the explicit correction and the implicit single-active-window replacement apply one typed policy to uncertainties that target the replaced window: an identical typed window payload (kind, value, start, end) keeps the uncertainty and its id, re-pointed to the replacement; the same canonical kind (`relative_day`, `relative_week` or `absolute`) with a different value retires it; a cross-kind change or a free-text `named_period` difference is unknown and keeps the question, re-pointed, so a question is never hidden. No clock, calendar resolution or prose is consulted. Any other active operational dependent of a replaced window rejects the replacement atomically with a typed policy error. Repair of historical duplicate active windows keeps its existing selection and deduplication policy; their window-targeted questions follow the same typed policy.

**Reference integrity on write, tolerance on read (both architectures).** The semantic commit checks its final canonicalized and corrected result, before staging, for newly introduced active operational references to inactive facts (identified by fact, target and source property relative to the original graph) and rejects the turn atomically if it finds one. Correction and decision history may keep old targets. The check is never part of the Fact Graph value validator, the session codecs or checkpoint preparation, so otherwise valid historical sessions are not rejected solely for inherited inactive references (normal schema, value, owner and budget checks still apply). Window questions that earlier builds left targeting a superseded window are ignored by the active scheduler projection and reconciled by the window policy above at the next accepted write, together with a pending question bound to them; other inherited dangling references are tolerated unchanged. When a contextual quantity-role answer replaces a workload, its active dependents are handled through the existing typed correction-dependent policy before the old workload is retired: same-unit per-unit pace and session length carry, total duration invalidates, and unsupported dependents reject atomically (see the fidelity map).

Provider failure, malformed output, validation failure or repair failure does not authorize legacy-parser fallback. Semantic repair is at most once where this contract permits it.

## Acceptance and recovery validation

Provider deltas and persisted Fact Graphs use different envelopes. `weeklyPlanningSemanticBaseValidatorV5.ts` and its extension wrapper own provider keys, local IDs, evidence, references and cross-field semantic checks. `weeklyPlanningFactGraphValidatorV5.ts` owns saved graph IDs, provenance, revision, lifecycle and references. Do not validate a saved fact by pretending it is an entire provider object, or require provider-only fields on historical saved facts.

Both adapters call the same value validators for task/context/component payloads, quantities, effort, recurrence, temporal/date rules, planning windows, availability, relations, source requests, uncertainty and correction/decision intent payloads. These kernels validate existing typed values; they do not interpret raw text, resolve calendar policy, grant approval, or decide scheduling. Absence (`no_additional_constraint`) and daily capacity are distinct availability variants. Reduced saved date rules and legacy optional extension fields retain their own envelope contracts. Exact fields, allowed values and compatibility cases are owned by types and executable tests, not a second schema copied into this document.

A schema-shaped but invalid value must not become accepted state merely because it came from another provider or from storage. The semantic validators return a rejected result with errors; normal repair/fallback policy still owns the next action and must revalidate repaired output. Unknown values must not silently become a different relation, source action or acceptance/rejection decision. Uncertainty field/reason remain nonempty free strings. Correction removal forbids a replacement, while modification/replacement requires an addressable replacement. Saved reference kinds retain the availability-correction compatibility adapter; the canonical writer continues to exclude proposal decisions from the persisted planning graph. Recovery does not grant approval authority. This does not introduce a partial-commit feature or make every unresolved fact invalid: supported `unknown`, nullable and symbolic representations remain accepted where their existing contract permits them.

`prepareWeeklyPlanningStableV5Checkpoint` validates the graph before traversing or encoding it. Checkpoint reading routes through the graph parser before hydration, so saved input is revalidated rather than trusted as previously accepted. Validation covers stored historical facts too; filtering removed/superseded facts for scheduling is a separate step. Regression tests use canonical writers and real checkpoint preparation/save/load, preserving valid historical representations while rejecting malformed values. These entry gates complement downstream fail-closed scheduler checks; they do not replace them.

## Time semantics

Natural-language time meaning belongs to AI; calendar arithmetic and scheduler-facing temporal compilation belong to the deterministic application.

The request clock is distinct from UI `selectedDate`. New future-plan blocks must not be placed before the deterministic `notBefore` boundary.

A relative date can remain symbolic at the semantic boundary and be resolved deterministically from captured calendar context. Do not let renderer wording or current UI navigation become the source of date truth.

For accepted active date constraints used by movable-work placement, the application resolves supported date expressions and compiles task/component applicability into scheduler-facing absolute hard date bounds and preferred placements before downstream distribution/placement. Downstream placement consumes that compiled representation rather than independently re-resolving the same deadline / earliest-start / latest-end / preferred-window meaning from raw semantic facts. Task-level constraints may apply to component work; component-specific constraints must not leak to sibling components. Removed or superseded facts must not remain effective through a downstream re-read.

Unresolved or contradictory hard date constraints fail closed at scheduler-input compilation rather than being silently weakened.

A consultation answer may suggest a date, but an AI-generated suggested date is not an accepted temporal fact. It becomes scheduler-relevant only after explicit user adoption and normal Stable V5 binding/lifecycle processing.

## Quantity roles

Workload quantity roles are not interchangeable.

- `scope_total`: the whole bounded scope when one actually exists
- `completed`: already completed quantity
- `remaining`: remaining quantity supported or derived from accepted facts
- `target`: quantity the user wants this planning operation to accomplish/schedule
- `declared` / `unknown`: quantity whose planning role is not yet sufficiently resolved

Important consequences:

- `scope_total` and `completed` may deterministically imply a `remaining`, but they do not automatically choose the user's planning `target`.
- `completed` work is not rescheduled.
- if a specific `target` exists for the same planning scope, scheduler compilation must not blindly schedule all `remaining` in addition to that target.
- corrections to total/completed/target must invalidate stale derived progress consistently.
- input order must not change the converged bounded-progress truth.
- open-ended work must not receive an invented total merely to make arithmetic or scheduling easier.
- a user-stated total time for a task with no content quantity (no workload of any role on the task or its components) is that task's time budget, whether the semantic layer typed it as a minute/hour `target` workload or as the task's own `total_duration` estimate. The scheduler-facing graph (planning evaluation and the missing-work question) projects one exactly-sized minute `target` from a single positive task-level `total_duration` (identical restatements count once; contradictory totals and hard fixed intervals are not projected). It is not persisted, carries the estimate's evidence, and disappears as soon as any content quantity is accepted, after which the same estimate is that quantity's cost. Shared by both conversation architectures (real-UI scenario F, 2026-10-07: without it the registered-material scope question re-armed indefinitely).

For consultation questions containing calculable quantities, deterministic calculation remains the numeric authority. An answer model may explain a computed result but must not silently replace application-owned arithmetic with its own value.

## Work decomposition / atomicity

Task decomposition is typed semantic state, not a scheduler guess.

Current semantic representation distinguishes concepts such as:

```text
atomic
| decomposed
| needs_breakdown
```

Scheduler-facing work items distinguish at least:

```text
splittable
| atomic
| unknown
```

Rules:

- atomic work must not be divided solely because a placement window is shorter.
- only work represented as splittable may be mechanically chunked by scheduler policy.
- unknown/needs-breakdown is not permission to infer splittability from raw task text or subject keywords.
- when work structure is required for a safe/meaningful plan, the semantic/dialogue boundary resolves it before scheduler use.

## Fact Graph / lifecycle

Canonical commit is atomic. Validation failure leaves accepted state unchanged. Correction/replacement/supersession is explicit lifecycle; no-op does not create an unnecessary revision.

Derived facts remain derivations with source/basis. A correction to their basis must not leave stale derived truth active.

Planned consultation advice does not enter the canonical planning Fact Graph merely because an answer was generated. Advice remains advisory state until the user adopts a defined scope and deterministic promotion creates normal planning contributions.

## Repair agenda / dialogue progression

Not every uncertainty blocks the same boundary.

Deterministic application classifies what must be repaired now versus what can be deferred. A low-impact/non-blocking uncertainty may remain in a repair agenda while another required question is handled first, but deferred work must reopen before the boundary it can affect.

Defer/pass-over is not silent deletion of uncertainty and does not convert it into accepted fact.

See [Human Grounding Policy](../policies/human-grounding.md).

Consultation must not be implemented by sending the user through the normal planning slot-question sequence. When Issue #246 is implemented, the consultation contract owns which missing information is material to a useful recommendation; only recommendation-changing/blocking gaps should trigger targeted questions.

## Proposal / readiness / scheduler

A proposal is not a command.

```text
application candidate
→ renderer presents it
→ AI interprets the user response
→ application accepts / rejects / modifies
→ accepted policy may affect scheduling
```

Unaccepted proposals do not affect scheduling. Readiness, question necessity, authoritative occupied sources, placement and feasibility are application decisions.

When the resulting Stable V5 planning horizon is exactly seven days, scheduling uses six normal placement days plus a seventh reserve day and prioritizes normal days before reserve. The default/fallback horizon is not an unconditional seven-day cap: applicable hard temporal bounds can require a longer usable horizon, and the scheduler still enforces the compiled hard bounds across that horizon. Detailed horizon, balancing and scoring behavior is owned by current scheduler policy, not semantic truth.

Issue #246 extends the same proposal principle to AI-generated study advice. Advice acceptance means only that a user has adopted a scope into planning intent; it is not preview approval or save authorization. Promotion must return to the normal Stable V5 readiness/scheduler/preview path instead of letting the advice branch call the scheduler or persistence layer directly.

## Pending question presentation binding

The pending question (`lastQuestionContext`) is application state; the assistant text that shows it is presentation only. When a Stable V5 turn commits a message that presents a pending question, the turn controller binds that question to the committed assistant message: turn ID, message ID, the planning-state revision after the commit, the committed graph revision, and the machine-known accompaniments the renderer was given with it (response source, current-turn grounding mode, self-repair notice, counts of proposed/contested grounding interpretations, preview promotion control). The binding is written only through the accepted commit and is replaced or removed by every later commit.

The freshness is computed once per turn at turn start (`pendingQuestionPresentation`) and every consumer reads that single value: the semantic public state (`pendingQuestion` is offered to the model only when fresh, with the revision of the presenting commit rather than the current graph), the focused contextual shortcut, the contextual binder, the no-op retry and proposal decisions. Authorization continues to read the raw previous state conservatively. A later turn may treat the pending question as the one the user is replying to only when the binding is `fresh`: the turn-start planning-state revision equals the bound revision (no failed turn, approval message, appended message, edit or clear happened in between), the latest message is the bound assistant message, and the graph revision is unchanged. A missing binding (sessions saved before binding existed), a malformed binding, or any mismatch fails closed. Freshness says only that the question context is still the one committed with the latest message; the consumer must still re-validate that its target (for example a proposal) is active and unsuperseded. Two limits are part of the contract:

- Presentation evidence. With `responseSource: deterministic_fallback` the application's typed question text was shown. With `ai` the renderer echoed this question's typed action contract and passed validation, but whether its free text actually asks the question is not verified, and must not be inferred from the text with regex or keywords. A consumer that depends on the text having asked the question must treat the rendered text as untrusted context and cover non-presenting renders in its evaluation.
- Scope. Freshness is local to the planning state held by the submitting client. It does not detect a newer checkpoint written by another tab or device; that is the existing last-writer boundary of the conversation store, not something the binding resolves.



The binding is not semantic input. It is excluded from the semantic model's public state summary and from renderer input, and it grants no approval, save, scheduler or lifecycle authority.

## Conversation interaction: three responsibilities (Issue #488)

The turn is described by three responsibility boundaries inside the one Stable V5 pipeline. They are **not** three LLM services and there is no outer conversation orchestrator or tool loop.

```text
semantic / conversation interpretation   (the one AI owner of raw Japanese)
  planning delta + typed conversationActs
↕
deterministic interaction / application controller
  typed acts + machine state + presentation freshness → turn outcome
↕
deterministic planner / persistence
  Fact Graph, readiness, scheduler, preview, approval, save
```

- **Typed conversational acts.** The semantic document may carry additive, non-exclusive `conversationActs` next to the planning delta: `answer_pending_question`, `ask_about_pending_question`, `topic_shift`, `resume_topic` and `consultation_request`. An ordinary planning turn has none. An act is discourse metadata of the current turn: only its kind and an optional topic reference (an existing active task/component id). It carries no quoted evidence (the application knows which turn it belongs to), no planning payload and no authority: it never feeds authorization, readiness, preview, approval or save, and a missing or wrong act can only degrade a turn into an ordinary non-mutating one. Mixed turns keep both the planning contribution and the act. `consultation_request` also requests bounded planning advice from read-only evidence below. The full Issue #246 advice/proposal/adoption runtime remains deferred; the act never adopts an alternative or grants planning authority.
- **Acts are validated apart from the planning delta (one response, two parts).** Every existing planning validator (schema, evidence/provenance, references, numeric safety, correction/decision targets) applies to the planning delta unchanged; act problems are never planning errors. A malformed entry (unknown kind, extra key, malformed target, non-array or oversized list) is dropped on its own (fail closed); an unknown topic reference degrades to "no topic". When the planning delta is still unusable after the single permitted repair (or the repair call itself fails), a valid self-sufficient act from those responses carries the turn as an accepted document with an EMPTY delta (`conversationOnly`): nothing from the rejected planning part is applied, and when it carried planning content the renderer is told those details were not taken in. A bare `answer_pending_question` never carries a turn. No second model call is made. The work-breakdown response contract (a pending breakdown question requires the target task to be restated) does not apply to a response without any planning content, so an explanation request is never rejected merely because it changes nothing.
- **Interaction outcome.** The application decides `apply`, `explain_pending_question`, `aside`, `resume_pending_question` or `recover` from typed acts and machine state only (never raw text). It may redirect which open question is presented when the user names an existing topic, or keep presenting the question the user asked about, but never pulls forward an issue the repair policy deferred this turn and never names a topic that is not an active fact of this conversation. `explain` is valid only for a fresh, unchanged pending question: in a mixed turn whose other details would change which question comes first, the asked-about question stays presented while it is still open, so the details are taken in and the question is still explained (a question that is stale, answered or deferred is not kept, and the turn is ordinary). An `aside` keeps the machine question but neither re-presents nor re-binds it; `resume` re-presents explicitly. A result carrying a preview is always `apply` (so an explanation or aside next to a kept preview is answered as an ordinary preview/status turn; a separate product decision). The narrow focused answer route has no channel for acts, so in the interaction architecture it falls back to the general interpretation when the message also asks for advice, asks about the question or changes the topic (still one semantic owner). A conversation-only turn behaves like an empty planning turn: it can complete a preview the user had already authorized, never authorize one.
- **Communication context (deterministic WHAT, renderer HOW).** With the outcome the application hands the renderer a typed `communication` context: the goal of the reply (`ask_question`, `report_status`, `present_preview`, `explain_question`, `acknowledge_aside`, `resume_question`, `clarify_turn`), machine-owned purpose codes saying why the planner needs what the question asks (`questionPurposes`, plus `laterNeeds` for other open questions), whether the reply asks the question, the typed status reason (`ready_to_create_preview` / `preview_unchanged`, reported by routing), the application-owned preview disclosure (work that did not fit), `planningDetailsNotApplied` and `consultationDeferred`. Every question code maps to a purpose (compiler-checked). Corrections reach the renderer as typed before/after data, removals made in this turn as `removedThisTurn`, and facts accepted in this turn as `currentTurnGrounding` (shared with legacy); when an acknowledgement of them is required it opens the reply and the goal (for example the explanation) follows it. None of this is prose and none of it is derived from raw text; the renderer must not decide the goal from the user message. The renderer is instructed to acknowledge only typed `acceptedFacts`: unaccepted times, days and quantities from the user message may be asked about, but never echoed as received. It does not explain a question unless the goal is `explain_question` (act accuracy and reply naturalness are evaluated separately).
- **Bounded planning consultation.** A consultation with no independent planning change is an `aside` when no preview is carried: the held question remains machine-owned but is not re-presented or rebound. Mixed turns retain their validated planning delta and the normal question/preview decision; preview-carrying turns remain `apply`. Optional `consultation` evidence is scoped to the accepted plan: work estimates, open question codes, daily upper limits, a next action and `fits` / `does_not_fit` only from this turn's actual scheduler result. A retained preview or compiler readiness alone supplies no fresh feasibility proof. Daily limits are not measured free time. The renderer may give conditional practical advice, but an unaccepted weekend/time alternative stays unassessed and unadopted; no extra scheduling call, new Fact Graph fact, authorization or save follows from the advice. Non-consultation replies omit this optional context. Interaction renderer responses carry strict `feasibilityClaim` metadata (`none`, `fits`, `does_not_fit`); a consultation verdict must match the application evidence or it is rejected as `unchecked_consultation_feasibility` with one repair. Prompt instructions forbid positive feasibility wording for unchecked alternatives; the metadata check never creates planning authority and real-model wording remains an evaluation gate.
- **Fixed-event-only conversations.** AI planning creates no savable event: a non-study fixed commitment or an unavailable window is busy-time evidence, never a preview candidate. In interaction mode, once every required question is resolved and the compiled plan has no movable work, the application stops re-inviting more work. For this purpose a question that targets only the planning window is suspended by a read-only projection: when no active study task exists and compiling the active graph without window-targeted questions yields no movable work and no other blocking issue (a resolved empty plan, or a fixed-only plan in which every task has a fixed reservation), the window question is not asked. The stored graph is unchanged, required task/component/workload/date and commitment questions keep precedence, and adding study work makes the original window question block again before any preview. Two additive, non-mutating acts carry the user's meaning: `request_event_registration` (wants an event added) and `decline_additional_work` (nothing more to add). A requested event gets one handoff, `fixed_event_manual_entry`, that names the existing 「予定を追加」 control and claims no registration; a declined optional invitation, or a later unchanged turn, gets `no_additional_work` and no question. In `interaction_v1`, a resolved empty conversation with no task or busy/fixed evidence also returns `no_additional_work` when a typed `decline_additional_work` answers a previously presented optional `missing_schedulable_work` invitation; subsequent unchanged replies stay quiet, required questions retain precedence, and later study work resumes ordinary planning without a save claim. The same typed decline also closes the invitation in any plan whose tasks are all non-study, whether or not their commitments resolved to fixed reservations (for example commitments outside the window), and it takes precedence over the manual-entry handoff (round 4, live X1). A `missing_schedulable_work` question about a non-study task pinned by a hard fixed interval asks for study work (the `missing_task_identity` intent), never for that commitment's progress; that wording is a typed renderer instruction and provisional. Busy-time-only statements get a `clarify_schedule_request` invitation, never an event handoff; `confirm_existing_schedule` is reserved for required commitment/source questions, which keep precedence. The terminal-state check on the renderer's own reply (no question mark or listed invitation phrasing; the handoff names the control, the acknowledgement does not) is an output presentation guard, never applied to user text; it is intentionally incomplete and fails toward the fixed application wording. Legacy keeps its historical behavior.
- **Actual preview condition truth.** On a new preview, optional `previewConstraintSatisfaction` is projected from active accepted facts, compiled scheduling input and the candidates actually exposed. Task/component and plan-wide preferred windows, soft available windows and session lengths are `satisfied`, `not_satisfied` or `not_evaluated`; applicable alternative windows form a union for each task, so a candidate need not occur in every per-day alternative; accepting a preference does not prove placement honored it. While any condition is unmet or unverified, the output guard rejects timing/condition descriptions for every task: a sentence that names a satisfied task can still describe the unmet one by alias or 「も」, so naming a task does not scope the check. Exact task labels are removed before the check only so a task whose own name contains such a word is not taken for a claim. With unmet conditions a neutral acknowledgement may cite accepted fact ids without repeating values, so the ACK contract does not force a rejected timing statement. An unverified constraint claim uses `unverified_preview_constraint_claim` and gets one renderer repair before emergency fallback. The application states the affected condition next to the reply in both rendered and emergency paths. Optional `allocationBreakdown` describes those same actual candidates; allocation arithmetic and the preview's estimate/margin label are owned by the [scheduling policy](../policies/scheduling.md#estimated-effort-and-allocated-time), and when this breakdown is present the renderer mentions neither estimate nor margin (including zero margin), leaving their explanation to the application display. `previewCount` counts candidate blocks inside one preview; the instruction describes N candidates, never N separate previews or alternatives.
- **Preview basis and claims.** When a repair question prevents a new preview, a kept partial preview survives only if all newly active scheduling facts concern brand-new work. Adding plan-wide availability/period/source facts or scheduling facts/relations on existing work invalidates the old preview atomically with the accepted graph change, even without superseding a prior fact. Unrelated additive work may keep a partial preview non-promotable. A rejected correction preserves accepted state; its recovery cannot describe the proposed quantity as the current preview. An unchanged-preview claim requires the application-owned `preview_unchanged` status. New/changed candidates and direct placement claims require a new preview; renderer text is never used to decide freshness. In interaction mode, a semantic recovery that kept the preview gets one application-owned sentence that the preview was not changed, appended beside the reply and in the emergency text; the renderer is told not to describe the preview, and a rendered unchanged claim is still repaired, because it cannot be checked for unaccepted values. A proposed-days what-if whose alternative differs from the current preview withholds the promotion control and asks the user to adopt the alternative explicitly; a reply that still names the control gets one repair and then the fallback. The difference is computed from a renderer-only ingress projection of the current preview (count, task ids, dates; missing placement provenance counts as different), which is never sent to the semantic model or persisted as planning state. Legacy unchanged.
- **Renderer writes every reply; emergency wording and application-owned disclosures.** Ordinary turns, explanations, asides, resumes, statuses, previews and semantic-failure recoveries are all written by the renderer from that context. Its prompt forbids describing the app's internals. Its output is rejected (one repair, then fallback) when it uses internal system/process vocabulary that neither the user said nor a plan label contains (machine keys and enum values of the plan data never count; snake_case codes always do), when it must ask the question (`askQuestion`) but contains no question (the question is bound to the reply as presented), or when it names work the scheduler left entirely out of a preview. Which work did not fit is scheduling truth, not wording: the application states it in its own sentence next to the rendered preview reply (`weeklyPlanningPreviewOmissionDisclosure.ts`), so no reply can claim such work is included. Only when the renderer cannot run (provider failure or outage gate, unexpected failure) or its output fails validation does the user see the short emergency wording of `weeklyPlanningInteractionFallbackText.ts`, composed from the same typed context around the application-typed question text (the shared typed question, date-interpretation and correction texts); it takes no routing status or preview sentence as input (typecheck-enforced), so such a sentence can never reach the user verbatim. Emergency composition, shared typed question/correction text and the application-owned omitted-work/unmet-condition disclosures are fixed wording. The disclosures also appear next to healthy renderer replies; they are application statements of scheduling evidence, not emergency conversation templates. The source-scan contract classifies these literals and checks the emergency wording for internal vocabulary. Round 4 adds two typed, prompt-level (provisional) instructions: a semantic-failure recovery says nothing about the request's content or feasibility, and a one-block preview (typed `previewCount`) is never described as a split.
- **Split-session and collective-preference meaning.** The interaction semantic instruction preserves an existing workload's total when the user asks to split it, unless the total itself is explicitly changed. Per-session length is `session_duration` and the stated session count is `recurrence.count`, not a replacement workload. A preference referring to both/all tasks is represented on each referenced task. The model owns this interpretation; deterministic code does not repair it by parsing the user's Japanese. The compact instruction has an explicit maximum 350-byte growth allowance in the semantic prompt-budget test; it is not an unrestricted budget increase. A total divided across named periods is a split too: keep the total, emit `session_duration` = total/periods and one `preferred_window` per period (round 4, live X5, where one total with two soft windows was placed as one block). The interaction rule grew 446 → 591 B under a 600 B per-rule cap. Compliance is model behaviour that only a live round can show.
- **Work-item titles name amounts with a trustworthy unit (shared by both architectures).** A title composes an application-computed amount with a unit. Clock units are named from the typed code (分/時間) because the amount is in that unit; any other coded unit keeps the model's `unitLabel` unless it contains an ASCII or full-width digit (a literal check of a typed field), in which case the code's canonical label is used; a digit-bearing `custom` label omits the quantity phrase. This removes 「903時間」 (live E) and amount echoes such as 「32220語」. Legacy titles change only for clock labels other than 分/時間 and for digit-bearing labels; clean labels are byte-identical. Residual: kanji-numeral echoes (「三時間」) are not detected.
- **Required question resolution.** In interaction mode, a planning delta resolves a required uncertainty only in that uncertainty's own dimension on its exact bound target. Material identity requires a new material component. Work breakdown and free-form unknown uncertainty fields share one structural-evidence predicate: a new constituent, or a new content (non-clock) quantity on the bound task or its components; a replay recognised by the typed restatement binding, a task shell, a rate, an effort/session answer, a clock budget or a sibling contribution never qualifies. Work breakdown is also answered by the accepted task-time-budget contract. An effort/session answer does not retire a material question. Contextual binding and commit-time reconciliation share this rule; independent details are accepted while the question remains open. Interaction uncertainties also carry a model-declared `blocksPlanning` flag (interaction schema only): `false` on a free-form field means the open point does not block scheduling, so it is not committed (no question, no block, no persisted field); the known structural fields (`WEEKLY_PLANNING_KNOWN_UNCERTAINTY_FIELDS_V5`: planning window, constraint source, work breakdown, material identity, quantity role, amount and the three effort kinds) ignore `false`, because their readiness is deterministic; an absent flag means blocking (round 4, live X3/H). Residuals: a free-form field that means material (the live B provider's `"material"`) can be waived by the flag; a required structure question still has no end state when the user cannot give structure; an advisory point that is not a consultation is not mentioned; whether the model sets the flag well is shown only by live rounds.
- **A blocking free-form question ends (release, not resolution).** In interaction mode a free-form (not known-field) blocking uncertainty U that is the fresh, presented `semantic_uncertainty` question is **released** when the next reading does not re-declare U, is not a structural resolution, and either (i) carries `answer_pending_question` bound to U's task (a component target maps to its task; an act target that names the uncertainty itself is degraded to unbound by the act contract) and adds a temporal constraint or recurrence on that task that the active graph does not already hold (typed replay identity), or (ii) is entirely empty after the existing bounded no-op retry: no delta anywhere and no act other than `answer_pending_question` (none is needed, because live readings of a plain go-ahead carry `conversationActs: []`; a consultation, explanation, topic-shift or resume act keeps U open). A rate, effort, session or clock answer, a replay, a task shell, a concern signal, a delta on another target or plan-wide availability never releases; known fields keep the rule above. A release is a distinct lifecycle operation (`released-free-form-uncertainty`, or `released-free-form-uncertainty-no-delta` for (ii)), never a resolution, and it is never silent: the application states 「「{the user's quote}」については未確定のまま進めます。」 beside the reply, on every outcome (a preview, another question or a capacity question), and for (ii) it adds 「この返事からは新しい条件を読み取っていません。条件があれば、あらためて教えてください。」, so a condition the readings dropped is visible; the renderer is told not to call the point settled. A later reading that re-declares a released point (same field and target) from a quote the current user text does not carry is dropped before canonicalization (`released-uncertainty-not-reraised`); when the current text carries the quote, the user raised it again and it blocks as before (Issue #488 H-release; critic probes 31 and 33). The free-form question itself is asked neutrally in interaction mode (「「{quote}」について、まだ決まっていない点があります。決まっていれば教えてください。このまま進めてよければ、そう伝えてください。」, renderer purpose `confirm_open_point`); known fields and legacy keep their wording, and the generic consultation notice is not repeated when the open point is on the consultation's task. Residuals: a placement bound to the uncertainty id does not release (live round 4 bound all 10 answer acts to tasks); a re-declaration under a renamed field blocks again; an effort-only bound answer keeps the question; a free-form field that means material, or an unrelated empty reply such as a thank-you, releases with the disclosure; the go-ahead invitation depends on the model reading a go-ahead as empty or as a bound answer (live: not yet exercised).
- **Bounded representation repair.** Interaction mode projects an exact owner-scoped registered-material id on a new matching material component into ordinary creation, rather than binding the bookshelf id as an active graph id. Normal schema/evidence/reference validators still run. A valid accepted-fact acknowledgement present in renderer metadata may be composed before the reply and the complete output revalidated; unsafe/unaccepted acknowledgements still repair or fall back. These two mechanical projections remove avoidable repair calls without a second semantic owner.
- **Evidence coverage selects an AI completeness audit, not meaning.** Round 4b: on the accepted-task-modification route, a workload quote with more literal digit runs (ASCII/full-width, counted, never read) than its typed numbers (the amount plus any range bounds) earns no coverage, so the stated-but-untyped number keeps the gap visible and the existing audit runs (live X3-T3, where the rate 「1章40分」 sat inside the workload's quote; provisional: effort quotes and kanji numerals are not covered, and recovering the number still depends on the audit and re-read). The quote of an uncertainty dropped as non-blocking (`blocksPlanning:false`, free-form field) still counts as covered. The interaction audit prompt also states that a request for advice or feasibility is covered by a `consultation_request` (provisional; live H-T2 showed the audit listing a consultation as a missing fact). Because acts carry no quote, an act-only consultation on a modification turn can still cost one audit call (residual). The completeness abstention `{route, reason, step}` is persisted in the turn diagnostic for every selecting route. Interaction mode reuses the existing completeness audit when the validated document cites at least one leaf fact, its literal source spans leave a contiguous gap of at least eight Unicode code points, and a discarded canonical graph projection's existing cost compiler would ask for a missing effort estimate on target/remaining work. Aggregate task quotes do not count as leaf coverage. This generic rule is span arithmetic without keywords, character classes, tokenization or raw-language inference; the semantic model still supplies every missing meaning. The interaction-only focused answer for an open material/pace question applies a stricter literal test before its narrow answer may stand: material coverage is anchored only on literal occurrences of the validated label (never on the model's quoted source span), an effort quote counts only when each of its non-digit runs is shorter than eight code points, and a remaining contiguous gap of four code points or any uncovered ASCII/full-width digit makes the focused answer incomplete. These literal classes only send the turn to the general semantic interpretation (one more AI dispatch, no extra repair); they never establish, bind or reject meaning. Known residuals: kanji numerals, short digit-free remainders and short non-material text inside a bounded effort span. For a nonempty document whose tasks all bind active accepted public ids, the generic rule's leaf citation and eight-code-point gap also make the existing audit eligible without the missing-effort condition when at least one task carries workload (including component workload), effort, temporal or recurrence changes; an identity-only accepted sibling does not prevent this. Outside this accepted-task-modification route, complete or stated-time-budget work pays no extra coverage audit. A malformed audit, provider failure or exhausted dispatch budget abstains and retains the valid initial document; normal validators and the shared turn budget remain authoritative.
- **A completeness re-read retains the initial planning facts.** In interaction mode, every completeness re-read, whichever route selected its audit (literal evidence coverage, the size-gated dense audit or a post-no-op recheck), including its repaired result, may add meaning but must retain the valid initial document's planning facts as owner-scoped multisets. Task count cannot decrease. Retained facts include task category; component role, normalized label and parent edges; workload value/role/unit together with its material owner; effort, temporal constraints and recurrence together with their typed target; and uncertainty, correction, decision and relation control references. Planning-window, availability, constraint-source and user-context facts are retained too. Accepted tasks retain their public owner id; new tasks require one unique typed-containing match with overlapping literal source spans. Provider-local ids are resolved before comparison. A component-to-task workload move is accepted only when material ownership remains unambiguous: exactly one material component in both readings. A changed or lost retained fact keeps the valid initial document, recording trace-only `completenessAbstention.reason=initial_facts_not_preserved`. If the retry is invalid and the shared repair ledger is already spent, keep that floor with `repair_budget_consumed` and dispatch no second repair. Purpose, activity kind, decomposition status and descriptive non-planning conversation metadata may be refined outside this floor. These checks validate structured meaning and literal evidence; they do not interpret language. Legacy behavior is unchanged: a legacy dense re-read still replaces the initial reading (known residual; an independent audit of `ad1e7784` showed a lossy dense re-read silently dropping a captured task there). The floor never blocks a later turn's explicit correction. A kept floor after a possible omission is not silent on these completion paths: when the turn could not take the content in or could not check it (its re-read was refused, an invalid re-read met a spent repair ledger, the re-read could not run after an incomplete audit, the accepted re-read or repair after an incomplete audit added no typed fact to the first reading, or the audit selected by a literal gap could not run or returned no valid decision), the application appends one typed sentence that some content may not have been read and invites the user to name what is missing. A first reading that points at the accepted plan without carrying a change, and whose recovering re-read is invalid but may carry a change (its lenient reading has planning content, or it cannot be read at all), is an unusable message (semantic recovery: nothing applied, the application's unchanged-preview sentence, no promotion control), never an unchanged plan; an invalid re-read that is readable and carries no planning content keeps the valid unchanged reading, unless the first reading carried typed content that existing-entity binding discards (see **No-op retry**). Known residuals (unresolved): an accepted re-read or repair that adds an unrelated typed fact but not the reported one counts as taken in (closing this needs a model-typed omission-to-fact mapping); a size-gated dense audit without a literal gap that the dispatch budget skips stays silent and unverified; omissions that are never detected stay silent (literal-coverage detection). The audit's free-text hints are never shown, interpreted or sent to the renderer; the renderer only learns that it must not claim everything was taken in.
- **Bounded numeric coverage after accepted-task changes.** On short (non-dense) interaction turns only, the accepted-task-modification audit route bounds workload amounts (including component workloads), every effort-estimate kind including session duration, and recurrences with a count: a quote contributes literal coverage only when each non-digit run is shorter than eight Unicode code points. Before bounding a workload quote only, remove literal occurrences of that same task's typed material component labels from the validated document and the bound accepted task's active committed components, plus that accepted task's active committed title. Current-turn titles, other tasks' names and non-material component labels are never anchors. Effort and recurrence quotes keep the plain ASCII/full-width-digit bound. A validated numeric fact with an excluded literal current-turn quote still satisfies the cited-leaf precondition even when zero points are covered; a truly empty no-op remains ineligible. In both the initial-valid and generic-repair branches, an accepted no-op re-read re-evaluates this short accepted-task-modification coverage route once, never the size-gated dense route. The audit candidate and retention floor remain the validated document, while the existing audit-selected re-read replays the provider response exactly as received by the semantic client rather than serializing the canonical document; transient raw-response plumbing adds no persisted field. A run-scoped guard permits at most one completeness audit per interaction turn. The audit adds one dispatch when complete, or selects the existing re-read with one further dispatch when incomplete, within the unchanged pool of eight and renderer reserve of one. Retention and the shared one-repair ledger still apply: an invalid re-read after a spent repair keeps the accepted re-read document with `repair_budget_consumed` and sends no second repair. Temporal constraints and material components retain ordinary literal coverage. Known residuals: a whole-utterance quote on either kind may suppress the gap, as may short non-numeric text inside a bounded numeric span or unrecognized numeral characters. Default generic coverage, focused-answer behavior and legacy behavior are unchanged.
- **Audit-authored registered-material timebox exception.** In interaction mode only, the already-selected completeness audit may author one additive minimal study-time task per uniquely identified registered material that the current turn explicitly names with a total time budget. Every other audit output remains advisory. The typed candidate carries its exact registered label, literal current-turn source and own numeric citation, amount, minute/hour unit and precision; deterministic code validates the citation, converts the typed unit, and requires a positive safe integer minute total. It never recovers a duration from raw language, saved progress or pace. The task has no material components, content counts or progress; existing tasks and active committed material facts take precedence, and overlapping current-turn task source spans veto addition. The merged document passes the entire existing validation boundary. Rejection discards the candidate without invoking a repair. Typed omission accounting skips the existing re-read only when every omission is covered by an accepted candidate; otherwise the existing re-read and at most one repair remain, their fact-retention check runs first, and the candidate is added only if the selected document still lacks that material. Ambiguous registered work without an accepted time budget keeps its scope question. Trace-only authorship records the selected phase, local task/effort ids, source and value text, and drop reasons in the existing bounded audit envelope; persisted fact sources stay `origin=user` and no stored graph format changes. Known residuals: a task quote spanning the whole utterance may veto completion; minute/hour interpretation remains model-typed.
- **No-op retry.** A schema-valid empty delta under a pending question is retried (bounded) only when it is a contradiction (`answer_pending_question` without any delta, or no act at all); a self-sufficient act (explain / topic shift / resume / consultation) is a valid result and triggers no completeness retry. Without a pending question, a first reading that names accepted tasks without a planning delta but carries typed content that existing-entity binding discards (a non-null title, category, study purpose or context label that differs from the accepted state) is an unusable message when its single re-read is invalid, empty, or carries no delta and no self-sufficient act: nothing is applied, the application's unchanged-preview sentence is shown and no promotion is offered (round 4, live B T4, where 「青チャートのこと」 was dropped and reported as unchanged). A bare shell identical to the accepted state (an acknowledgement) keeps the unchanged plan. This turns a silent loss into a disclosed safe failure; it does not take the content in. Residuals: a content-bearing message that the model reads as a shell identical to the accepted state is still reported as unchanged, because it cannot be told apart from an acknowledgement until a typed acknowledgement/no-change act exists (silent loss); the discarded set is duplicated from the binding; the activity kind is not compared; every acknowledgement shell still costs one re-read call.
- **Empty readings (x6).** One typed predicate defines an empty reading: no delta anywhere (an existing-entity shell with nothing in it counts as empty) and no act the renderer answers (a bare `answer_pending_question` counts as empty). In interaction mode, once a plan is accepted, an entirely empty **first** reading is re-read once, like a task shell (live H r1 on `fd6a29fd` returned `tasks: []` for 「じゃあ水曜の夜にまとめて」 and the placement was dropped); legacy eligibility is unchanged. A task-less `create_plan` first reading on that path is the typed creation authorization and is not re-read; a re-read after a contradiction is never taken as one (the B-T4 unusable-message recover stands), and under a pending question eligibility is unchanged in both architectures (pinned by a 96-combination table against the previous logic). When the turn's final reading is empty (and is not a creation authorization), under an accepted plan or a pending question, the application appends 「この返事からは新しい条件を読み取っていません。条件があれば、あらためて教えてください。」 once beside its reply (`communicationFacts.nothingRead`); a free-form release by an empty reading shows the same sentence once, not twice. Cost: one extra semantic call for an empty acknowledgement under a plan. Residuals: a typed acknowledgement act (which would remove that call) is parked for lack of evidence and prompt headroom; a re-read can still fail on the model's references (live H r1 on `80af22a3`: a disclosed 「その変更は使えませんでした」).
- **Placement is a function of the accepted state; capacity claims are checked deadline-first (shared, both architectures).** Compiled work items follow the accepted task order (stable within a task), so a corrected or later-added workload does not move to the end of the placement order. When the greedy, all-or-nothing first pass leaves work unplaced, the scheduler retries once with the earliest hard deadline first (stable) before returning `insufficient_capacity`. A plan that places on the first pass is unchanged. One extra deterministic pass, no AI call (exam-student B1: a 30→20 correction on a retained preview had claimed insufficient capacity for a feasible plan). Residual: a plan feasible only by reordering within one deadline class, or by backtracking.
- **The user's own month events are busy time (shared, both architectures).** Persisted, owner-checked, busy MonthEvent occurrences (from the canonical occurrence projection: repeats, multi-day spans, 24:00) are placement busy time with the same ±10-minute buffer as Plan rows, independent of any constraint-source request. The request-gated external sources remain for genuine external calendars. Other owners' events are ignored, never an error. **Interim policy, pending the user's product decision:** an all-day entry (the editor's shape, starting 00:00 and ending 24:00, 00:00 or 23:59) and a date-only entry do not block unless explicitly `busy: true`, so note-like entries such as 「テスト期間」 do not silently remove planning days. Timed spans, including multi-day trips, block (exam-student B2: MonthEvent-backed buffers were placed over). Options for the user: all-day blocks; non-blocking unless flagged (the interim, needing an editor busy toggle); or blocks with the withheld days named.
- **An overload states what did not fit (interaction).** On `insufficient_capacity` the application carries a typed `capacityShortfall` (the plan's total required minutes, the unmet minutes, and up to five unmet tasks with a trustworthy quantity phrase and minutes) in the communication facts. The application states it in its own sentence (「入りきらなかった作業: …。今回の計画に必要な時間は合計N分です。」), never as a shortfall against free time, which the scheduler does not expose. The renderer is told not to state the figures (prompt-level, provisional). Numbers only, no labels, are persisted in the trace (exam-student B3).
- **Corrections never silently delete turn-created content (shared, both architectures; a legacy control exercises the rule).** Applying corrections may delete a turn-created fact (a fact a replacement hangs from, or an orphaned component, task or study context) only when it is typed-redundant with the surviving graph. A redundant workload equals an active workload of the same task or component. A component is redundant when it matches the target's role and label and has no active children. A task container is redundant when it matches the target's category and study context and has no active child. Anything else rejects the transaction, so the turn becomes a disclosed recover with the plan unchanged and the application's sentence. A correction's own replacement is never pruned. In interaction mode, validation also reports a replacement that hangs from an uninstalled new workload (`support-not-installed`), and the one repair is told to install it with a replace correction or keep it as new work. That repair is provisional (live X5-T2; critic probes 28 and 29). An orphan task container is redundant only when its title, study purpose and context label equal the target's, and no active child remains. A rename carried by a new container (for example 「数学の宿題」) is therefore content, and the turn becomes a disclosed recover (critic probe 30). Residuals: the activity kind is not stored on study contexts, so it is not compared; there is no task-rename operation, so a stated rename is disclosed as not applied rather than taken in; a pure re-declaration of the existing total with a session correction hanging from it is rejected at binding (disclosed, not applied).
- **Same-turn corrections are order-independent across a dependent migration (explicit shared fix, both architectures; x9a).** When one correction of a turn replaces a workload, its dependent migration supersedes the efforts hanging from it. A later correction of the same turn that names such an effort is applied to the migrated fact (the transaction's own migration identity), and a replacement effort that hangs from the workload another correction installs keeps that target. A target superseded in an earlier turn, or within the turn by anything other than this transaction's dependent migration, is still rejected (pinned at the unit level with the earlier gates bypassed). Before this fix the outcome depended on the order of the corrections (live round 5 X5 T2: workload then effort was rejected with `target-fact-not-active`, while the reverse order applied); legacy pins assert the new, order-independent result, because the legacy oracle has no such scenario.
- **Restated accepted workloads keep their identity.** In interaction mode, a task-level workload that restates the one active accepted workload of its bound task, where that workload sits on a component, binds to the accepted fact (binding and current-turn provenance share one predicate): quantity role, per-occurrence flag, amount and unit code must match exactly, unit label and component placement are ignored, and the nullable period/range fields are tolerated only when null on the restatement side. An ambiguous match binds nothing. So a restatement keeps the accepted rate and effort instead of becoming a rateless new workload (round 4b, live H-T3). Residuals (provisional overall): a component-level restatement of a task-level workload (the reverse direction) and a genuinely repeated identical amount are not covered.
- **One semantic repair per turn (interaction ledger).** In interaction mode, when a rejected quote (empty or not grounded in the current text) lies under a task bound to an accepted entity (`existingPublicId`), the one repair is told not to restate that entity and to return only current-turn changes, each quoted from the current text (round 4, live D T3; typed by validation path and binding; root-cause for the repair stage, provisional overall because the first reading's restatement is the model's). A per-run repair ledger enforces the AGENTS.md limit across every repair entry: the generic repair route, the focused date/window/temporal-scope repair routes and the focused material answer mark it immediately before dispatch and refuse once it is spent. Re-reads (dense, completeness and no-op) are not repairs and do not mark it; a repair they trigger goes through a marking entry. In interaction mode, an invalid final no-op re-read gets the turn's single repair while the ledger is unspent (error-keyed directives; the repaired reading must be valid, preserve the re-read's valid meaning and carry a delta or a self-sufficient act), so a repairable re-read is no longer lost with no repair used (round 4b, live X2-T3). After a consumed focused repair returns a fallback or an invalid result, the turn may still make one general (non-repair) interpretation call with no repair left; a transport failure keeps the provider-failure recovery instead. Final diagnostics report the repair. Legacy retry behavior is unchanged.
- **One turn dispatch pool.** Every provider dispatch of a turn (focused routes, generic call, repair, completeness/dense audit, renderer) draws from one turn-scoped pool (`WEEKLY_PLANNING_TURN_AI_DISPATCH_LIMIT`, renderer reserve 1). Stages do not own stacking retry allowances. Exhaustion keeps an already valid semantic result and never becomes a connectivity failure; renderer exhaustion falls back to the emergency wording. Outage gate: while the turn's latest provider dispatch has failed, the enforced (interaction) pool refuses the renderer, so a turn that continues after a provider failure (for example a conversation-only rescue after the repair call failed) uses the emergency wording instead of waiting on the provider that just failed; semantic stages are never gated and a later successful dispatch reopens it. A failed renderer repair dispatch always ends in the fallback (shared adapter fix).
- **Conversational recovery.** A provider failure or a semantic/validation/canonicalization failure keeps the accepted graph, preview and machine state exactly (the retained state is the turn-start snapshot). Recovery is a typed `recover` outcome, not an application-written paragraph. Only when the previous question's presentation was `fresh` and the application has typed text for it is that same question re-presented and its presentation rebound to the recovery message; otherwise nothing is re-presented and no binding is written (fail closed). A semantic failure is rendered like any reply (`clarify_turn`: say briefly and naturally that the message could not be used, then the retained question or an invitation to continue); a provider failure is not rendered (the same provider just failed) and shows the short emergency wording: with a re-presented question it asks only that question (one request), otherwise it asks for a resend. Neither asks to resend after a semantic failure, invents a content question, explains the app's processing or exposes validator/provider payloads. The projected result and trace describe the retained state; they do not claim questions were cleared.
- **Proposal decisions.** A decision on a learning-strategy proposal changes its status only when it targets the proposal of the fresh presented question. This tightens the earlier "any pending proposal" behavior: a collective decision no longer settles a proposal the user was not shown (relevant to the Issue #152 V09 note); the other proposal stays pending until its own question is presented. In interaction mode a presented proposal that the next turn does not decide lapses only when that turn applied a planning change (a non-empty semantic diff), so an optional offer no longer stalls the plan (round 4, live X2). An empty reading, an acknowledgement shell, a recovered turn or an aside keeps it held and re-presented. A lapsed proposal stays `pending` with `decidedAtTurnId` naming the closing turn (no new persisted literal or key), is omitted from the model context, is never reported as declined or accepted, and is not re-presented, including on the capacity path. Residuals: a lapsed proposal cannot be re-offered on request; `decidedAtTurnId` is overloaded as the closing turn.


Deferred (not part of this change): generic evidence references and replay of a failed utterance (relative-date replay would need the original request clock), a durable freshness-reason diagnostic, and the Issue #246 consultation runtime.

## Runtime conversation architecture mode (Issue #488 comparison switch)

Two conversation architectures exist side by side so the Issue #488 interaction model can be compared honestly with what it replaced. The mode changes **conversation interpretation and presentation only**; neither mode weakens Fact Graph validation/provenance, revision/idempotency, scheduler/preview safety, explicit save approval or owner/chat isolation, and `legacy_v5` is the pre-#488 *conversation* architecture, not an older checkout (unrelated main/security fixes are kept).

- `interaction_v1` — the three-responsibility model above. **Default for new conversations.**
- `legacy_v5` — the Stable V5 conversation/control flow as of `ee07697e`.

**One policy owner, no mixtures.** `weeklyPlanningConversationArchitecture.ts` defines the typed mode and the capability policy derived from it (`conversationArchitecturePolicy`); there is no per-feature toggle, so a conversation can never run a mixture. `weeklyPlanningConversationArchitecturePreference.ts` is the only module that reads `VITE_WEEKLY_PLANNING_CONVERSATION_ARCHITECTURE_DEFAULT`, `VITE_WEEKLY_PLANNING_ARCHITECTURE_SWITCH_ENABLED` and the browser preference (a source-scan test enforces this). The mode is decided once per turn by the turn controller and then travels as a typed value in the turn input (`conversationArchitecture`): executor → Stable V5 runtime → semantic pipeline/normalizer input, validation input, dialogue render input. Nothing downstream inspects env, storage or query strings.

**Invariant the codecs rely on.** Loading materializes `legacy_v5` for a stored state that has an admitted turn (`conversationRequestSequence`, intake state, drafts or preview candidates) but no field, so the stored and in-memory forms are identical (the AI-planning module-reload readback compares them). In production an unpinned state acquires such turn-derived content only through `begin_turn` (which pins) or through codec hydration; draft blocks come only from turn-produced previews. A future non-turn path that adds such content must pin, or it reintroduces a readback mismatch (`load → serialize` round-trip identity is tested for pinned and pre-field-with-turn states). A state with no admitted turn (empty, or only an appended notice) stays unpinned.

**Session pinning.** `PlanningState.conversationArchitecture` (`'legacy_v5' | 'interaction_v1'`, strictly validated by both codecs; no free text) is written by the reducer at the first admitted turn (`begin_turn`) and never rewritten. Therefore it survives reload, chat A → B → A snapshots and week/session persistence. An empty conversation is unpinned; a new conversation (`reset_session`, new chat) captures the then-current default exactly once, at its first turn. Changing the preference or the build default never touches an existing conversation. A stored checkpoint that has an admitted turn (`conversationRequestSequence > 0`, an intake state, drafts or preview candidates) but no field was authored under the old architecture and hydrates as `legacy_v5` (never silently migrated into interaction semantics); a state without any admitted turn (empty, or only an appended notice) stays unpinned so its stored and in-memory forms are identical. The preference (`studyplanner.weeklyPlanning.conversationArchitecturePreference.v1`, `{version:1, architecture}`) is a per-device default for new conversations only, is honoured only while the evaluation gate is on, and is not planning state.

**Code rollback hazard.** Builds from before this switch have strict codecs that reject any `PlanningState` carrying `conversationArchitecture`: the weekly storage codec loads it as an empty conversation (and the next save can overwrite it); the session/chat codec makes the snapshot unreadable. Because hydration materializes the key, merely opening an old conversation on the new build can write `conversationArchitecture` at its next checkpoint, after which a pre-switch build cannot read it. Only conversations that were opened or ran a turn on a build with the switch carry the field; empty/untouched ones do not.

**Allocation-data rollback hazard (shared).** New preview candidates and draft blocks can carry `allocationBreakdown` in either architecture. Pre-#488 weekly localStorage readers with strict field lists reject this property even when no architecture pin is present, load an empty conversation, and can overwrite the retained data on a later save. Selecting `legacy_v5` in a new build does not remove shared allocation evidence or make those old readers compatible. The new codecs read historical field-absent data and the new evidence; reader-first compatibility/cutover or an explicit release decision on old-build/old-tab risk remains unresolved. The pin-specific session/chat hazard above is separate; the critic's allocation-only session-codec probe remained readable. Release assessment must cover each actual reader rather than generalize one codec's result.

**Rollback / comparison semantics.** Rolling back is switching the next new conversation to `legacy_v5` (or setting the build default); existing conversations keep their mode. Measurements compare conversations of different modes on the same scenario; they are not planning truth and are not a substitute for the real-model/human gate.

## Availability

Existing StudyPlanner plans and timetable are authoritative busy sources in current production. Accepted hard availability/life constraints and the request-time `notBefore` boundary reduce candidate space; preferences/personalization do not create free time.

Required-source failure is not equivalent to a successfully loaded empty source. Sleep end does not necessarily imply study-available start.

See [Availability Architecture](weekly-planning-availability-architecture-v5.md) and [Scheduling Policy](../policies/scheduling.md).

A consultation answer may consume a deterministic capacity/availability summary when it materially affects advice. The answer model does not become an independent owner of free-time calculation or feasibility.

## Human grounding and memory

Application-only knowledge is not automatically shared ground. Current-week acceptance, durable preference and observed learning evidence are distinct states. One week-local acceptance is not promoted to a durable preference without the required scope/consent.

Authoritative app data may be used as grounded known context so the user can be asked for additions/deltas rather than forced to restate known facts. Renderer must not invent fields absent from that data.

AI-generated consultation advice is not durable user memory. If the user separately expresses durable meaning such as `今後もこの方法でやりたい`, the existing user-context/memory authority owns that promotion.

## Preview / approval / save

Preview is unsaved and bound to owner, conversation, graph revision and source facts. A semantic change after preview requires a fresh preview. AI output alone cannot bypass approval/save.

If saving only part of an approved batch succeeds, the remaining draft snapshot keeps a versioned local recovery receipt containing the available frozen batch payloads and original operation membership/identity. Previously acknowledged items may lack payloads in an older partial snapshot only when the retained operation records their saved Plan IDs. Both compatibility and Stable V5 checkpoint boundaries validate and retain it; their compact representation stores each payload once and resolves unique remaining-block references before validation. A retry rechecks owner, current revision, conversation/runtime and assumptions against the original batch; it never constructs a new operation from a smaller remainder. Confirmed items disappear from the preview, while unresolved payloads stay unchanged until retry or explicit session reset. A failed finalization retains the completed receipt so the next attempt only finalizes, without re-saving items. Clearing a session does not undo already committed Plans.

The receipt is recovery evidence, not approval authority or AI input. Its frozen draft payloads remain in owner-scoped local session/chat storage and are excluded from approval trace and outcome telemetry to avoid duplicating titles, memo and material details. Existing operation IDs, item results and counts remain the diagnostic evidence. Server Plan/item identity and atomic-save rules are unchanged. Historical remainder-only snapshots that already lost the original batch cannot be reconstructed unambiguously; this does not claim retroactive recovery for them.

Pending assumptions, deferred repair that still affects preview/save, stale source revisions or unaccepted proposals must not silently become saved truth.

Consultation advice is upstream of preview. Displaying or persisting advice alone must not create a preview. A preview can be produced only after accepted advice scope has been promoted and normal readiness requirements are satisfied.

## Persistence / trace / security

Persisted/session state is owner- and conversation-bound. The public conversation-import facade accepts unknown input and owns canonical codec validation before runtime hydration, controller reset or state/storage mutation. Invalid or oversized snapshots return false without changing the current session; callers do not need to pre-parse or remember an internal validation sequence. In-memory recovery snapshots use the same compact wire representation for size validation as storage, without silently trimming imported messages. Trace is diagnostic evidence, not authorization or planning truth. Untrusted stored strings remain data rather than instructions.

Saved component ancestry must reference components in the same task and contain no parent cycles. Provider-local and canonical stored IDs share the same cycle policy; each boundary owns reference/ownership diagnostics. Historical removed or superseded facts retain their valid parent links, with lifecycle availability evaluated separately. Invalid ancestry is rejected before checkpoint/import acceptance rather than repaired by dropping links.

Saved workloads may have no component, or reference a component of their own task. Temporal constraints and recurrence facts target their own task or one of its components, including in retained history; date rules continue to target their containing task. Live effort estimates must target a task, component or workload owned by that same task. Explicitly removed/superseded effort facts retain correction provenance: a historical estimate can keep its original task while its referenced replacement workload has been rebased. Preserve that terminal history and its existing target references; do not reactivate it or rewrite it to satisfy a live-fact constraint. Lifecycle status tags must be literal supported strings, not values accepted through string coercion.

A single owner/application-lifetime chat facade owns the active index and checkpoint/navigation ordering; UI surfaces consume its immutable index and typed outcomes instead of rebuilding snapshot/index steps. The live application state remains the sole unsaved conversation authority. A view-only remount reconnects to that session without re-importing older disk state. Unavailable index or active-snapshot reads are distinct from an absent store: initialization must bind successfully before checkpoint writes can adopt an existing chat. Retry reattempts that binding, while an explicitly confirmed new conversation may preserve an unreadable old chat without overwriting it.

A completed preview edit must update its restorable chat snapshot before control returns to navigation; rendering frames are not a persistence boundary. An authoritative empty conversation must replace an older non-empty chat snapshot, while a pending or invalid chat-snapshot update must not overwrite it. Chat export may explicitly include a validated empty checkpoint; the ordinary session-store policy may still omit empty checkpoints. Empty state and unavailable export are distinct outcomes. If a required snapshot/index write fails, keep live state, report a retryable failure and block conversation replacement. Optional search-cache failure does not invalidate snapshot success. Ordinary surface navigation remains available because the live session outlives the view; a dirty-only document-exit warning cannot guarantee recovery after a forced reload/browser kill. Destination validation and runtime ownership checks precede index writes; delete cleanup follows a successful index update. Session-generation and lifetime checks also revoke callbacks across A→B→A owner changes and application unmount.

Unreadable weekly-planning checkpoints are opaque user data, including malformed JSON, future versions, unknown fields, and owner-validation failures. Stable and compatibility load, save, empty-state clearing, failed-save fallback, and previous-week cleanup must classify the existing bytes before removing or replacing them. Store and read back an exact copy in the separate `studyplanner.weeklyPlanningUnreadable.v1` namespace first. Keep only the newest capture per owner/week, with a 2 MiB limit on its complete serialized envelope. If quota, size, read-back, or source-change checks prevent a verified backup, retain the original and block mutation of that checkpoint; the protection does not create an owner-wide write guard. An invalid incoming owner never authorizes deletion of existing data. The active-session index is disposable navigation metadata, not a user snapshot.

Roll-forward recovery discovers retained data by owner/week without relying on that index and revalidates it using the current codecs. Restore exact bytes only when neither storage format has an active conversation in that owner/week. A readable retained copy with the same conversation ID and strictly older savedAt than the active checkpoint is stale and may be discarded. Every other active-conversation conflict keeps the copy and exposes a typed recovery status. Unreadable copies remain retained. Ordinary migration, checkpoint clearing, approved-plan persistence, and trace/outbox scans do not include this namespace; raw retained data never becomes AI or diagnostic communication.

The direct Stable V5 session-save API rejects an invalid graph without overwriting the existing checkpoint bytes. This is not an application-wide promise to retain an old checkpoint: `saveOwnedWeeklyPlanningState` clears a readable Stable checkpoint and persists compatibility state when the direct save returns false; an unreadable checkpoint must first pass the retention boundary above. Valid empty-state removal and quota-compaction policies also remain separate. Keep tests and reports explicit about which storage boundary they establish.

When consultation is implemented, advice/context/retrieval strings remain untrusted data. If prompt, request/response, trace or persisted session fields change, the feature-local `src/features/weeklyPlanning/AGENTS.md` trace persistence gate applies.

### AI runtime module recovery

The application loads the AI-turn runtime before OCR, clearing the composer, or beginning a turn. A module-load failure keeps input local and permits one explicit code-only retry; it never retries OCR, provider execution, approval, or persistence. Awaited preflight is bound to committed planner inputs and the current owner/chat/state lifetime, including A→B→A transitions. It must not admit a retained request after those inputs change.

Planner collections are admitted through the owner/reset and accepted-projection lease supplied with those exact arrays, as defined by [Planner read projection recovery](../../client-runtime/architecture/planner-read-projection-recovery.md). Check that lease against live readiness before and after module preflight and again after OCR at admission; becoming ready on a newer projection never validates an older request. A revoked lease must produce a data-changed explanation while retaining exact input and the attachment, with no automatic resend or module-recovery misclassification. Pending read recovery disables submission while leaving the draft and conversation accessible. This adds no cancellation guarantee after turn admission.

A separate explicit reload action first checkpoints and re-reads the canonical chat snapshot/index, then verifies a small per-tab recovery capsule in sessionStorage. The capsule is versioned, bound to owner/chat/conversation/week/state revision, limited to 2 MiB of serialized data and 30 minutes, and contains exact composer text, projected starter metadata, and supported original image bytes. Revalidate the durable chat and current lifetime after asynchronous image serialization and immediately before reload. Quota, invalid data, oversized images, or failed checkpoint/read-back keep the current editable draft and block reload, with copy/reattach guidance. The ordinary 15 MiB attachment limit does not imply that every attachment fits this recovery capsule.

Restore only after canonical chat hydration, without overwriting a nonempty composer. Consume the exact capsule only after its draft has rendered. Revalidate restored starter references against the current catalog before OCR or submission; do not silently drop an unavailable target. Restoration never automatically sends a turn. The capsule is transient UI recovery, not Fact Graph authority, a durable conversation store, or diagnostic trace data. Preflight failures occur before turn admission and create no provider request/turn diagnostic; tests verify that boundary. Other lazy-loaded app surfaces and already-admitted runtime failures are separate responsibilities.
