# StudyPlanner 週間計画自然文入力・教育的ヒアリング QAテスト設計

## 目的

StudyPlanner の週間計画入力について、固定的な自然文だけでなく、人間が実際に入力しそうな曖昧な文章、情報不足、省略、誤字、順不同、話し言葉、教材量ベースの表現、試験予定表、作成後の修正指示を前提にしたテスト観点を整理する。

今回は実装修正ではなく、TDD のためのテスト設計を目的とする。

最終的に固定したい仕様は次の通り。

- 曖昧な入力でも、週間計画作成や学習計画作成の意図がありそうなら作成フローへ誘導する。
- 情報が不足している場合は、勝手に予定化せず、AI 側から確認質問を行う。
- ユーザーが分量・日数・時間帯を決めていなくても、質問を通じて作成画面まで到達できる。
- 時間ではなく、ページ数、問題数、単語数、単元名、教材名、試験範囲で入力されても、学習量として保持する。
- 学習量を時間へ換算する根拠が不足している場合は、1ページ何分、1問何分、単語何個を何分などを質問する。
- ユーザーが「分からない」と答えた場合は、仮置きしてよいか確認し、仮定を assumption として保持する。
- テスト対策では、試験日、科目、範囲、現在進捗、苦手度、配点、教材を確認して優先度を決める。
- テスト予定表や試験範囲表は、OCR 済みテキストまたは構造化データを fixture として受け取る前提にする。
- 一度計画を作った後でも、ユーザーの追加指示で再計画できる。
- 通常AI入力や通常予定保存導線へ誤爆しない。
- 既存予定・時間割・buffer などの配置制約は壊さない。
- まずテストで期待動作を固定し、その後に最小実装で通す。

## 参考にする考え方

### 7人のQAペルソナ

Zenn記事「Claude Code に『7人の意地悪なQA』を仕込んでテストケースの観点漏れを潰した」の考え方を参考にする。

AIに単にテストケースを考えさせると正常系に寄りやすいため、次のような複数視点で観点漏れを減らす。

- P1 新人ユーザー
- P2 ベテラン高速入力ユーザー
- P3 悪意ある操作者
- P4 データ整合性監査役
- P5 既存データ・移行担当
- P6 回帰デグレ番人
- P7 仕様懐疑者

StudyPlanner では、これを以下へ拡張する。

- P1 新人・曖昧ユーザー: 短文、説明を読まない、何を入れればよいか分からない。
- P2 高速・大量・教材量入力ユーザー: 省略、コピペ、改行、ページ数、問題数、単語数で入力する。
- P3 悪意・異常値ユーザー: 0時間、負数、極端値、非現実的速度、HTML風入力を入れる。
- P4 データ整合性監査役: 合計分数、scope、unit-rate、assumption、revision差分を見る。
- P5 既存データ・外部入力担当: 既存予定、時間割、OCR結果、古いplan、未承認draftの混在を見る。
- P6 回帰デグレ番人: 通常AI入力、通常予定保存、既存UI、既存テストの回帰を見る。
- P7 仕様懐疑者・教育妥当性レビュー: 実装が作った計画を信用せず、仕様と教育的妥当性を疑う。

### 教育的ヒアリング

学習計画では、ユーザーが最初から「科目・時間・日数・優先度・進捗」を揃えて入力するとは限らない。

実際には、次のような入力が多い。

```text
テスト対策したい
数学やばい
英単語やらないと
教科書30ページくらい進めたい
線形代数の固有値のところ
計算理論のオートマトンとチューリング機械
テスト予定表貼るからいい感じに組んで
まだどれくらい時間かかるか分からない
```

この場合、AI はすぐ予定を作るのではなく、以下を段階的に確認する。

1. 目的: 何のための計画か。
2. 期限: いつまでに必要か。
3. 範囲: どの科目・単元・ページ・問題・単語か。
4. 現在地: 今どこまで終わっているか。
5. 分量単位: ページ数、問題数、単語数、講義回、章、プリント枚数など。
6. 時間換算: 1ページ・1問・1単語セットに何分かかるか。
7. 優先度: 試験日、配点、苦手度、未着手度、締切を考慮する。
8. 制約: 既存予定、時間割、睡眠、食事、集中しやすい時間帯。
9. 仮定: 不明な値を仮置きする場合は、仮定として表示し、後で編集可能にする。
10. 再計画: 作成後の違和感や進捗遅れに応じて修正できる。

## 対象範囲

対象にするもの。

- 週間計画の自然文入力検出。
- 曖昧入力の解釈。
- 情報不足時の確認質問。
- 複数ターンの追加回答。
- 週間計画 draft 生成前の pending 状態。
- task / subject / duration / date range / preference の抽出。
- ページ数・問題数・単語数・教材名・単元名・試験範囲の抽出。
- 学習量から時間へ換算するための質問。
- テスト対策入力。
- テスト予定表・試験範囲・シラバス・画像OCR結果の受け取り。
- 科目ごとの優先度推定。
- 現在の進捗・苦手度・目標点・配点の保持。
- 曖昧語を仮定として扱うこと。
- 週間計画プレビュー作成。
- 作成後の追加指示による再計画。
- 一括承認・一括破棄前後の状態遷移。
- 通常AI入力への誤爆防止。
- 通常予定保存導線への影響防止。
- 既存予定・時間割・buffer との整合性。

対象外にするもの。

- OCR 自体の実装。
- Gemini OCR の実行。
- 画像処理の精度評価。
- 週間計画プレビューの CSS。
- DayTimeline / WeekView の通常UI表示調整。
- bufferMinutes の意味変更。
- hardViolationCount の意味変更。
- placement scoring の大規模改修。
- 既存テスト期待値の雑な変更。
- production code の修正。
- テストを通すためだけの本体実装変更。

OCR は別エンジン、例えば Gemini が担当する前提にし、StudyPlanner 側のテストでは OCR 後のテキストまたは構造化データを fixture として渡す。

## 重要な仕様方針

### 1. 曖昧入力は失敗ではなく pending 化する

入力例。

```text
来週勉強したい
テスト対策したい
数学やばい
英語やらないと
```

期待動作。

- 週間計画意図、または学習相談意図として扱う。
- すぐに確定 draft を作らない。
- 何が不足しているかを特定する。
- 次の質問を返す。
- pending state に会話文脈を保持する。

### 2. 学習量は時間に直変換しない

入力例。

```text
数学の教科書を30ページ進めたい
線形代数の問題を20問解きたい
英単語を300個覚えたい
```

期待動作。

- ページ数・問題数・単語数を scope として抽出する。
- ただし時間換算の根拠がない場合は、勝手に時間へ変換しない。
- `1ページ何分くらいかかりますか？`
- `1問に平均何分くらいかかりますか？`
- `英単語は何個を何分で覚える想定ですか？`
- このような質問を返す。
- ユーザーが「分からない」と答えた場合は、仮置きの許可を取る。

### 3. ざっくり表現は仮定として扱う

入力例。

```text
英語多め
数学は普通
卒研は毎日少し
いい感じに
できるだけ均等に
```

期待動作。

- `多め` `普通` `少し` `均等` を preference として保持する。
- 具体的な分数が未定なら、仮配分の確認を行う。
- 仮配分は assumption として preview に出す。
- ユーザーが後から修正できるようにする。

### 4. テスト対策は試験情報を優先して聞く

入力例。

```text
テスト対策をしたい
試験勉強の計画作って
テスト予定表貼るから組んで
```

期待動作。

- 科目名・時間だけを聞くのではなく、試験日、試験範囲、配点、現在進捗、苦手単元を確認する。
- 予定表画像がある場合は、OCR 後のテキストを入力として扱う。
- 早い試験、配点が高い科目、未着手、苦手、範囲が広い科目を優先する。
- それでも不明な場合は、仮優先度を提案して確認する。

### 5. 通常入力への誤爆を防ぐ

入力例。

```text
英語の勉強法を教えて
数学の問題を解説して
来週って英語で何？
勉強のやる気が出ない
計算理論のチューリング機械を説明して
```

期待動作。

- 通常AI入力として扱う。
- 週間計画 draft を作らない。
- 「仮予定」「一括承認」「一括破棄」などの週間計画 UI を出さない。
- `やりたい` や `勉強` という語だけで週間計画へ誤爆しない。

### 6. 週間計画モード内の短縮入力を補足回答として扱う

入力例。

```text
英語3時間、計算理論4時間
数学も2時間追加
卒研は多めで
Javaは余った時間に
```

期待動作。

- 週間計画モード内、または直前に週間計画 pending がある場合は補足回答として扱う。
- 通常モードでは誤爆しない。
- 前回 pending へ追加・更新する。
- 競合や曖昧さがある場合は確認する。

### 7. 作成後の修正を first-class に扱う

入力例。

```text
ちょっと違う
英語をもっと増やして
数学を朝に寄せて
卒研は毎日じゃなくて3日でいい
火曜は無理
全体的に詰まりすぎ
1回90分までにして
```

期待動作。

- 既存 draft をベースに再計画する。
- 保存済み plan を勝手に変更しない。
- 未承認 draft の場合は draft を更新する。
- 承認済み plan の場合は変更案を作り、確認してから反映する。
- 変更差分を説明する。
- 既存予定・時間割・buffer 制約を維持する。

## ヒアリング状態モデル

テストでは、自然文入力を以下の状態へ分類できることを確認する。

```text
idle
intent_detected
awaiting_subjects
awaiting_scope
awaiting_unit_rate
awaiting_deadline
awaiting_exam_schedule
awaiting_current_progress
awaiting_priority
awaiting_availability
ready_for_draft
preview_generated
revision_requested
ready_for_approval
approved
discarded
```

### 状態遷移例

```text
User: テスト対策したい
State: intent_detected -> awaiting_exam_schedule
App: テスト日程や範囲が分かるものはありますか？予定表や範囲表を貼ってください。

User: 予定表貼る
State: awaiting_exam_schedule -> awaiting_current_progress
App: OCR結果を確認しました。各科目で今どこまで進んでいますか？

User: 数学は半分、英語は単語がまだ
State: awaiting_current_progress -> awaiting_unit_rate
App: 英単語は何個を何分くらいで覚える想定ですか？分からなければ仮置きします。

User: 分からないから仮で
State: awaiting_unit_rate -> ready_for_draft
App: 仮定つきで週間計画プレビューを作成します。
```

## 教材量・学習量入力のテスト観点

### 数学・計算系

入力例。

```text
数学の教科書を30ページ進めたい
線形代数の固有値の単元をやりたい
演習問題を20問解きたい
計算理論のオートマトンの章を復習したい
```

期待動作。

- `数学` `線形代数` `計算理論` を subject として抽出する。
- `教科書30ページ` `固有値` `20問` `オートマトン` を scope として保持する。
- 時間未定なら unit-rate 質問へ進む。
- `1ページ何分くらいかかりますか？`
- `1問に平均何分くらいかかりますか？`
- `読むだけですか、例題を解きますか、演習までやりますか？`
- などを質問する。
- 分からない場合は、仮見積もりを提案してよいか確認する。

テスト候補。

| ID | 入力 | 期待 |
|---|---|---|
| EH-MATH-001 | 数学の教科書を30ページ進めたい | ページ数を scope に保持し、1ページあたり時間を質問 |
| EH-MATH-002 | 線形代数の固有値をやりたい | 単元名を保持し、範囲・教材・目標を質問 |
| EH-MATH-003 | 演習問題を20問解きたい | 問題数を保持し、1問あたり時間を質問 |
| EH-MATH-004 | 計算理論のオートマトンとチューリング機械 | 複数単元として保持し、優先度または時間を質問 |

### 英語・語学系

入力例。

```text
英単語を300個覚えたい
ターゲット1900を進めたい
英語長文を5題やりたい
英作文の対策したい
```

期待動作。

- `英単語` `長文` `英作文` など task type を抽出する。
- 単語数・長文題数を scope として保持する。
- 時間未定なら以下を質問する。
  - `新しく覚える単語ですか、復習ですか？`
  - `何個を何分で覚える想定ですか？`
  - `1長文に何分くらいかかりますか？`
  - `単語は復習日も入れますか？`
- 単語学習は1回で終わらせず、復習セッションを作る必要があるか確認する。

テスト候補。

| ID | 入力 | 期待 |
|---|---|---|
| EH-ENG-001 | 英単語を300個覚えたい | 単語数を保持し、単位時間または仮置きを質問 |
| EH-ENG-002 | ターゲット1900を進めたい | 教材名を保持し、範囲または開始位置を質問 |
| EH-ENG-003 | 英語長文を5題やりたい | 題数を保持し、1題あたり時間を質問 |
| EH-ENG-004 | 英作文の対策したい | task type を保持し、添削・例文暗記・演習の区別を質問 |

### レポート・卒研・制作系

入力例。

```text
レポート書かないと
卒研進めたい
Java実装やりたい
Obsidian整理したい
```

期待動作。

- 成果物がある作業として扱う。
- 完了条件を質問する。
- 分解可能なら調査、構成、執筆、見直し、提出などに分ける。
- 所要時間が分からない場合は、過去の作業時間や締切を聞く。

質問例。

```text
レポートは何文字・何ページ程度ですか？
締切はいつですか？
今は未着手、構成だけ、本文途中、見直し段階のどれですか？
```

## テスト対策モードの設計

### 予定表・範囲表入力

入力例。

```text
テスト対策したい
テスト予定表貼るから組んで
この画像の予定で来週の勉強計画作って
```

期待動作。

- OCR 自体は StudyPlanner で行わない。
- App は OCR 済みテキストまたは構造化データを受け取る前提。
- 画像だけの場合は「OCR結果を貼る」または外部OCRへ渡す導線を案内する。
- OCR 結果を受け取ったら、科目、試験日、範囲、持ち込み可否、配点などを抽出する。
- 不足情報があれば質問する。

OCR fixture 例。

```text
7/4 数学 線形代数 第1章〜第4章 60分
7/6 英語 単語1-800 長文3題 50分
7/8 計算理論 オートマトン・正規表現・CFG 90分
```

期待。

- 7/4 の数学を最優先にする。
- 7/6 の英語を次に置く。
- 7/8 の計算理論は数学・英語の後に配分する。
- 範囲が広く、未着手の科目は優先度を上げる。
- 進捗不明なら現在地を質問する。

### テスト対策ヒアリング項目

最低限聞く項目。

| 項目 | 理由 |
|---|---|
| 試験日 | 残り日数と優先順位に必要 |
| 科目 | タスク分割に必要 |
| 試験範囲 | 勉強量に必要 |
| 現在進捗 | 残量計算に必要 |
| 苦手度 | 優先度に必要 |
| 配点・重要度 | 時間配分に必要 |
| 目標点 | やり込み度に必要 |
| 使う教材 | ページ数・問題数・単語数へ落とすために必要 |
| 生活予定 | 可用時間計算に必要 |

### テスト対策の優先度計算観点

テストでは、具体的なアルゴリズムの完全一致ではなく、以下の優先関係を固定する。

- 試験日が近い科目は優先度が高い。
- 配点が高い科目は優先度が高い。
- 未着手の科目は優先度が高い。
- 苦手度が高い科目は優先度が高い。
- 範囲が広い科目は優先度が高い。
- ただし、すべてを高優先にせず、確認可能な理由を diagnostics に残す。

テスト候補。

| ID | 前提 | 期待 |
|---|---|---|
| EH-EXAM-001 | 試験日が近い数学、遠い英語 | 数学を先に配置 |
| EH-EXAM-002 | 英語は配点高、数学は配点低 | 英語の配分が増える |
| EH-EXAM-003 | 計算理論が未着手 | 計算理論の優先度理由に未着手が残る |
| EH-EXAM-004 | OCR結果に試験日なし | 試験日を質問し、確定 draft にしない |
| EH-EXAM-005 | 範囲表だけで進捗不明 | 現在進捗を質問する |

## 再計画・修正指示のテスト観点

作成後の計画は一発で正解にならないことを前提にする。

### 修正入力例

```text
なんか違う
英語をもっと増やして
数学は朝にして
火曜は無理
1回90分までにして
卒研は毎日じゃなくて3日にまとめて
計算理論をもっと細かく分けて
全体的に詰まりすぎ
夜は集中できない
```

### 期待動作

- 直前の週間計画 draft を修正対象として認識する。
- 保存済み plan を勝手に変更しない。
- 未承認 draft は再生成または差分更新する。
- 承認済み plan の場合は変更案として出し、確認後に反映する。
- 変更前後の差分を説明する。
- 既存予定・時間割・buffer は維持する。
- 変更指示で指定された制約を diagnostics に残す。

テスト候補。

| ID | 入力 | 期待 |
|---|---|---|
| EH-REV-001 | 英語をもっと増やして | 英語の合計時間または優先度が増える |
| EH-REV-002 | 数学は朝にして | 数学が午前 slot 優先になる |
| EH-REV-003 | 火曜は無理 | 火曜の draft を避ける |
| EH-REV-004 | 1回90分まで | maxSessionMinutes が90へ更新される |

## 進化版 P1〜P7 QAペルソナ

### P1 新人・曖昧ユーザー

説明を読まず、短く曖昧に入力するユーザー。

入力例。

```text
来週勉強したい

何からやればいい？

数学やばい
英語やらないと

```

期待動作。

- 明示的に「計画」「予定」「来週」がある場合は週間計画へ誘導する。
- `テスト対策したい` で `awaiting_exam_schedule` または `awaiting_subjects` へ進む。
- `数学やばい` で「数学の何をいつまでに？」と質問する。
- `いい感じに` は確定条件ではなく preference として扱う。
- 科目や時間が不足している場合は確認質問を返す。
- 通常予定として即保存しない。
- 入力が空に近い場合でも、失敗ではなく次の入力例を提示する。

テスト候補。

- `来週勉強計画を作りたい` で確認質問が表示される。
- `英語と数学やりたい` は週間計画モード内なら補足入力として受け付ける。
- 通常モードでは `英語と数学やりたい` だけで週間計画に誤爆しない。
- 情報不足時に draft block を確定しない。
- `テスト対策したい` で試験情報を質問する。

### P2 高速・大量・教材量入力ユーザー

短縮表記・大量入力・コピペ・連打・教材量入力を行うユーザー。

入力例。

```text
来週 英語10h 数学8h 卒研6h Java4h
来週、英語10、数学8、卒研6くらい
英語3h 計算理論4h 線形2h 統計2h
数学 p20-50、英単語300、計算理論 3章と4章
線形20問 統計15問 英語長文5題
英語10h
数学8h
卒研6h
Java4h
```

期待動作。

- `h` 表記を時間として解釈する。
- 半角・全角・読点なしでもできるだけ抽出する。
- 改行区切りでも抽出する。
- ページ数・問題数・単語数を落とさず scope として保持する。
- 時間換算が不明なら unit-rate 質問へ進む。
- 科目数が多くても欠落しない。
- 送信連打で pending / draft が二重生成されない。
- 120分超は既存方針通り分割する。
- 合計分数を保持する。

テスト候補。

- `英語10h 数学8h` を `英語600分 数学480分` として抽出できる。
- 大量科目入力で全科目が欠落しない。
- Enter連打または送信ボタン連打で pending が1つだけ生成される。
- コピペの改行入り入力でも抽出できる。
- `p20-50` をページ範囲として保持する。
- `英単語300` を単語数として保持する。

### P3 悪意・異常値ユーザー

異常値・不正値・過剰入力を行うユーザー。

入力例。

```text
来週、英語を0時間、数学を-1時間やりたい
卒研を999時間やりたい
英単語-300個
数学9999ページ
1ページ0分で
```

期待動作。

- 0時間・負の時間は確定 block にしない。
- 負数・0分・非現実的速度は確定しない。
- 極端な時間や量は確認またはエラー扱いにする。
- 同一科目重複は合算するか、確認質問を返す。
- 記号やHTML風文字列で表示や保存が壊れない。
- XSS 的な文字列は文字列として扱い、HTMLとして解釈しない。
- 無限ループや極端な処理時間を起こさない。

テスト候補。

- 0時間・負数で block が生成されない。
- 999時間で確認質問が出る。
- 数学9999ページで確認質問が出る。
- 1ページ0分で確定しない。
- 英単語300個を1分で覚える指定は非現実的速度として確認する。
- `<script>` を含むタイトルが HTML として実行されない。

### P4 データ整合性監査役

画面表示ではなく、内部データの整合性を見る。

期待動作。

- 分割前後で合計分数が変わらない。
- 120分超のセッションは分割される。
- 30分未満の block は作られない。
- title / subject / memo が分割後も維持される。
- `30ページ * 5分 = 150分` のような換算根拠を diagnostics に残す。
- 仮置き値は assumption として保持する。
- ユーザーが後で `1ページ10分だった` と言ったら再計算される。
- 再計画後も元の scope が失われない。
- 承認前は未保存 draft として扱う。
- 承認済み plan と未承認 draft が混ざらない。
- 一括破棄後は draft が残らない。
- 一括承認後は通常 PlanDraft 形式へ変換される。

テスト候補。

- 合計分数保存。
- 120分超分割。
- 30分未満 block 禁止。
- title / subject / memo 維持。
- unit-rate の換算根拠保持。
- assumption の保持。
- 再計画後の scope 維持。
- 一括破棄で pending が空になる。
- 一括承認で通常 PlanDraft 形式へ変換される。
- 承認前に保存済み plan と混同されない。

### P5 既存データ・外部入力担当

既存予定・時間割・古いデータ・OCR結果がある状態を見る。

前提データ。

- 保存済み予定あり。
- active 時間割 template あり。
- 既存予定前後 buffer あり。
- 古い plan 形式が混在。
- 未保存 weekly draft が残っている。
- OCR結果が不完全。
- OCR結果に誤字や欠損がある。

期待動作。

- 既存予定と重ならない。
- active 時間割 template と重ならない。
- buffer は配置制約として使う。
- ただし buffer は通常UIに表示しない。
- OCR結果が不完全でも落ちない。
- OCR結果に日付や科目が欠けている場合は質問する。
- 古いデータが混在しても落ちない。
- 保存済み plan と未保存 draft を混同しない。

テスト候補。

- 既存予定を hard constraint として扱う。
- active 時間割 template を busy interval として扱う。
- buffer 込みで衝突しない。
- buffer 表示用の余計なカードを作らない。
- 古い plan shape でも例外を投げない。
- OCR結果の欠損を質問へ変換する。

### P7 仕様懐疑者・教育妥当性レビュー

実装が仕様と一致しているかを疑う。

観点。

- `来週` の基準日は `SELECTED_DATE` で固定されるべき。
- wall-clock に依存して flaky にならない。
- 6日間配分・7日目予備日が仕様ならテストで固定する。
- 情報不足時に勝手に仮定しすぎない。
- ただし、質問により作成画面へ誘導する。
- 分からない値を勝手に決めていないか。
- 仮定をユーザーに見せているか。
- テスト日程・範囲・進捗を聞かずにテスト対策計画を作っていないか。
- 学習量から時間への換算根拠があるか。
- 再計画で元の制約を壊していないか。
- 既存予定と buffer を hard constraint として扱う。
- buffer は通常UIで目立って表示しない。
- 未保存 draft と保存済み予定を混同しない。

テスト候補。

- `SELECTED_DATE = '2026-06-19'` で週境界が固定される。
- `来週` の解釈が実行日で変わらない。
- 情報不足時は確認質問を返し、保存しない。
- ユーザーの追加回答で pending が完成する。
- 承認するまで通常予定として保存されない。
- 仮定が assumption として残る。
- テスト対策で進捗確認なしに確定しない。

## テスト記述方針

このプロジェクトは Vitest を使っているため、Jest ではなく Vitest 前提で書く。

```ts
import { describe, expect, it, test, vi } from 'vitest';
```

複数入力の表形式テストには `test.each` を使う。

```ts
test.each([
  {
    id: 'EH-MATH-001',
    input: '数学の教科書を30ページ進めたい',
    expectedState: 'awaiting_unit_rate',
  },
  {
    id: 'EH-ENG-001',
    input: '英単語を300個覚えたい',
    expectedState: 'awaiting_unit_rate',
  },
])('$id $input', ({ input, expectedState }) => {
  const result = parseWeeklyEducationalHearingInput(input);
  expect(result.nextState).toBe(expectedState);
});
```

日付は固定する。

```ts
const SELECTED_DATE = '2026-06-19';
```

wall-clock に依存するテストは flaky になるため避ける。

OCR は fixture として扱う。

```ts
const GEMINI_OCR_EXAM_SCHEDULE_TEXT = `
7/4 数学 線形代数 第1章〜第4章
7/6 英語 単語1-800 長文3題
7/8 計算理論 オートマトン CFG チューリング機械
`;
```

## まとめ

StudyPlanner の週間計画AIは、時間指定のパーサだけでは足りない。

実際の学習計画では、ユーザーは時間ではなく、ページ数・問題数・単語数・単元名・試験範囲・進捗・苦手度で話す。さらに、計画作成後に「なんか違う」と感じて修正したくなる。

そのため、テストで固定すべき中心は、自然文を一発で完全に解釈することではなく、曖昧さを検出し、適切な質問を返し、仮定を明示し、少しずつ計画作成画面へ近づける会話状態である。

この1ファイルを、週間計画自然文入力改善のTDD仕様書として扱う。
